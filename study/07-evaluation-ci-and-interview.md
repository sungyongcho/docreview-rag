# 7. 비교 평가·CI·면접 설명 완성하기

[전체 진행표](README.md) · 이전: [OAuth](06-auth0-and-external-mcp.md)

목표는 LangGraph+MCP가 실제로 무엇을 개선하고 어떤 비용을 추가했는지 측정하는 것이다. 성공 사례뿐 아니라 나빠진 사례와 아직 확인하지 못한 부분도 설명한다.

## 먼저 읽을 코드와 자료

- [evaluator.py](../app/evals/execution/evaluator.py): 기존 검색 평가의 실제 측정 범위
- [scoring.py](../app/evals/results/scoring.py): 검색 점수의 분자·분모
- [golden/models.py](../app/evals/golden/models.py): 질문·원문 구간·검토 상태 계약
- [data/golden/REVIEW.md](../data/golden/REVIEW.md): 기존 데이터 검토 안내
- [SEC EN](../data/golden/sec_en_v2_astra.json), [SEC KO](../data/golden/sec_ko_v2_astra.json), [DART KO](../data/golden/dart_retrieval_ko.json): 후보 질문

현재 검색 점수는 답변 정확성 점수가 아니다. 기존 데이터의 미검토 표시는 그대로 두고, 실제 원문 검토 근거를 별도로 확보한다. 타입을 바꿔 승인된 것처럼 보이게 하지 않는다.

## 비교할 네 경로

| 경로 | 측정 목적 |
|---|---|
| 단일 검색 RAG | 검색 한 번으로 답하는 기준선 |
| 기존 CLI 에이전트 루프 | 프레임워크 도입 전 도구 반복 기준선 |
| LangGraph + MCP | 최종 구현 |
| LangGraph + 직접 도구 호출 | MCP 통신 비용을 분리하는 평가 전용 대조군 |

현재 기본 웹 workflow가 곧 단일 검색 RAG라고 가정하지 않는다. 기준선의 모델 호출 수·프롬프트·검색 횟수를 명시한다. 기존 루프를 지우거나 평가 직전에 유리하게 바꾸지 않는다. 직접 호출 대조군은 별도 제품 실행 경로로 공개하지 않는다.

## 데이터와 실험 설계

1. 조회·수치·복합 질문·근거 없음 유형을 고른다. 최종 평가 목표는 **12개 질문 묶음 × 영어·한국어 = 24문항**이다.
2. 개발용 질문은 최종 평가 묶음과 분리한다. 같은 질문의 번역본·가까운 변형이 양쪽에 들어가지 않도록 묶음 단위로 나눈다.
3. 각 질문의 답과 근거를 원문에서 확인한다. 회사·연도·단위·원문 해시·구간을 확인하고 검토하지 못한 문항은 미검토로 둔다.
4. model ID, 공시 snapshot, 검색 설정, 예산, 프롬프트, 실행 코드 버전을 고정한다. 서로 다른 항목은 결과에 함께 적는다.
5. 작은 사전 실행으로 비용과 지연을 확인한다. 전체 완료에 필요한 남은 비용을 추정한 뒤 본평가에 들어간다.

네 경로를 모두 24문항에 적용하면 기본 실행은 96회다. 각 실행의 모델 호출 수는 더 많을 수 있다. 번역·임베딩·실패·재검증까지 합친 전체 한도는 **25 USD**다. 불명확하게 끝난 유료 요청은 자동 재시도하지 않는다. 예산 안에 끝내지 못하면 실제 완료 범위를 보고한다.

## 각각 보고할 지표

| 지표 | 판단 근거 |
|---|---|
| 답변 정확성 | 검토된 정답과 의미·숫자·단위 비교 |
| 인용 유효성 | 문서·청크·원문 해시·구간이 실제 원문과 일치 |
| 근거 충족 | 인용한 원문이 답변의 주장을 뒷받침 |
| `NOT_IN_DOCS` | 근거가 없는 질문에서 적절히 답변을 유보 |
| 오류·종료 사유 | 도구 실패, provider 실패, 예산 소진, 취소 등을 분리 |
| token·비용·지연 | 실제 사용량과 측정 시점, 추정 비용 기준 |

각 지표의 분모와 실패 문항 처리 방식을 먼저 정한다. 실패를 빼서 성공률을 높이거나, 인용 형식 통과를 정답으로 세지 않는다. 모델 호출 방식과 프롬프트도 달라졌다면 차이를 LangGraph 자체의 효과로 단정하지 않는다.

## CI 만들기

1. 비밀·개인정보를 제거한 모델 응답 기록과 그 요청 조건을 준비한다.
2. 재생은 모델 응답 경계에서만 한다. 실제 그래프·MCP transport·범위·인용·예산 로직을 실행한다.
3. 요청 조건·호출 순서·schema가 기록과 다르면 실패한다. 기록이 없을 때 실제 유료 모델로 넘어가지 않는다.
4. API 키를 주지 않은 환경에서도 재생 검사가 동작하고, 불일치 시 외부 호출이 없음을 확인한다.
5. stdio·HTTP 종료, 도구 실패, 취소, 체크포인트 재개, 인증 실패를 포함한다. 검색 통합은 격리된 PostgreSQL에서 `-m live_postgres --require-live-postgres`로 검증한다.
6. 영향받는 Python lint·format·type, web test·type·build, 변경한 프록시 경로 검사를 연결한다.

현재 CI 파일의 존재를 먼저 확인하고, 없으면 실제 필요한 workflow를 추가한다. 응답 재생은 회귀 검증이며 모델 성능 재측정이 아니다. 실제 성능 결과와 별도 보고한다.

## 영어 면접 실습

90초 설명을 직접 작성한다. 아래 문장은 답안을 대신하는 문장이 아니라 구성 틀이다.

```text
Problem: What could the original system do, and what was missing?
Design: What do the model, LangGraph, and MCP each own?
Evidence: What did you measure under a fixed budget?
Trade-off: Where did the new path become slower, costlier, or less reliable?
```

10분 시연은 정상 질문 → 실제 도구·근거 확인 → 근거 없는 질문 → 취소 또는 실패 → 비교 결과 순서로 준비한다. 이어서 코드를 보고 다음 과제를 직접 수행한다.

- 도구 입력의 제한 하나를 바꾸고 영향받는 검증을 수정한다.
- 그래프 분기 하나를 바꾸고 무한 반복이 생기지 않음을 확인한다.
- 변조된 citation과 잘못된 audience 오류를 각각 진단한다.
- “MCP 없이도 도구 호출이 되는데 왜 도입했는가?”에 답한다.
- “체크포인트가 유료 호출 중복 실행을 막아주는가?”에 답한다.

## 전체 완료 기준

- [ ] 0~6단계의 학습·구현·검증 상태가 확인된다.
- [ ] 최종 24문항의 원문 검토와 비교 결과가 있다. 미완료는 명시한다.
- [ ] 성능 저하 사례와 설계의 추가 비용을 설명한다.
- [ ] CI 재생 검증과 실제 성능 측정을 구분한다.
- [ ] 90초 설명, 10분 시연, 작은 변경, 인용·OAuth 오류 진단을 직접 통과한다.

이후 별도 자료 갱신 단계에서 마스터 프로필·자료 정책·이력서 카탈로그를 함께 반영한다. 개인 프로젝트 경험으로 명시하고 실제 측정한 결과만 사용하며, 과거 제출본은 보존한다. 가이드 작성이나 코드 구현만으로 이력서 반영까지 완료한 것으로 처리하지 않는다.
