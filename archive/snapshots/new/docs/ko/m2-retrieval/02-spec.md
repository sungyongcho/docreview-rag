# M2 명세

## 1. 범위

M2는 M1.4 단계에서 생성한 출처 인용이 포함된 `Document` 및 `Chunk` 행을 사용해야 합니다. 결정론적 임베딩 백필, 정확한 벡터 검색, PostgreSQL 전문 검색, 순위만 사용하는 융합, 선택적 재순위화 경계, 단일 세션 프로덕션 구성, 명령줄 인수 경로를 제공해야 합니다.

M2.1부터 M2.8까지의 기준선은 근사 벡터 인덱스를 생성하거나, PostgreSQL FTS를 문자 그대로의 BM25라고 주장하거나, BM25 순위 함수를 구현하거나, 평가를 수행하거나, M3의 최종 구성을 선택하거나, 기존 데이터베이스 스키마를 마이그레이션해서는 안 됩니다. 유예된 BM25 실험군은 15절에서 명시합니다.

## 2. 임베딩 계약

모든 공급자는 비동기 문서 및 쿼리 임베딩을 구현해야 합니다. 공급자 출력은 입력 순서를 유지하고, 입력마다 유한한 숫자형 벡터를 정확히 하나씩 포함해야 합니다.

데이터베이스와 공급자의 차원은 384 입니다. 프로덕션 공급자는 `text-embedding-3-small`에 `dimensions=384`와 float 인코딩을 지정해 요청해야 합니다. 오프라인 공급자는 안정적인 SHA-256 토큰 해싱을 사용하고, 네트워크 호출 없이 정규화된 384차원 벡터를 반환해야 합니다.

빈 문서 배치는 빈 목록을 반환합니다. 개별 빈 문자열, 잘못된 벡터 개수, 잘못된 차원, 불리언, 숫자가 아닌 구성 요소, NaN, 무한대는 유효하지 않습니다.

임베딩 백필은 다음 조건을 충족해야 합니다.

1. 임베딩이 null인 행만 청크 ID 오름차순으로 선택합니다. 2. 공급자 I/O 전에 선택 트랜잭션을 종료합니다. 3. 크기가 제한된 배치로 처리합니다. 4. 임베딩이 여전히 null이고 `index_text`가 변경되지 않은 행만 업데이트합니다. 5. 선택 수, 임베딩 수, 오래되어 건너뛴 수, 배치 수를 보고합니다. 6. 활성 트랜잭션이 없는 호출자 세션을 요구합니다.

공급자 식별 정보는 M2에 저장하지 않습니다. 데이터베이스 임베딩 집합과 그 집합을 대상으로 하는 모든 쿼리는 동일한 공급자 및 구성을 사용해야 합니다. 서로 다른 모델의 벡터는 관계 없는 공간에 있으므로 공급자를 바꾸면 모든 청크를 다시 임베딩해야 합니다. 섞어도 아무것도 발생하지 않고 계산 가능한 유사도가 반환되므로, M2에서 조용히 실패하는 유일한 계약입니다.

## 3. `ChunkHit`

`ChunkHit`은 고정된 Pydantic 값 객체입니다. 알 수 없는 필드는 거부합니다. 포함하는 필드는 다음과 같습니다.

| 필드 | 계약 |
|---|---|
| `chunk_id` | 양수인 `chunks.id` 대리 키 |
| `doc_id` | 비어 있지 않은 `documents.doc_id`, 최대 32자 |
| `item` | null일 수 있는 SEC Item, 값이 있으면 최대 8자 |
| `kind` | 정확히 `text` 또는 `table` |
| `citation` | 비어 있지 않은, 사람이 읽을 수 있는 공시 및 Item 레이블 |
| `start_char`, `end_char` | `0 <= start_char < end_char`를 만족하는 반열린 정규 출처 범위 |
| `source_sha256` | 정확히 64 자의 소문자 16진수 문자열 |
| `body` | 비어 있지 않은, 출처에서 파생된 근거 |
| `context_header` | 합성 검색 문맥이며 비어 있을 수 있음 |
| `index_text` | 문맥, 빈 줄 두 개, 본문을 정확히 결합한 값. 문맥이 비어 있으면 본문만 사용 |
| `score` | 범위가 전략별로 다른 유한한 전략 점수 |

이 계약은 `body` 대신 스니펫을 허용해서는 안 됩니다. 이후 단계에서 인용과 범위를 평가하려면 저장된 근거 전체가 필요합니다. 코사인 유사도, 텍스트 순위화, RRF, 재순위화는 하나의 척도를 공유하지 않으므로 점수를 `[0, 1]`로 제한하지 않습니다.

## 4. 검색 필터

`RetrievalFilters`는 고정되어 있으며 다음 필드를 지원합니다.

- 청크 차원: `doc_ids`, `items`, `kinds`
- 문서 차원: `tickers`, `fiscal_years`, `forms`

모든 필드는 튜플입니다. 빈 튜플은 제한이 없다는 뜻입니다. 한 필드에 값이 여러 개면 SQL 대안으로 처리하며, `items`에서는 명시적인 null 처리도 포함합니다. 값이 있는 필드끼리는 SQL `AND` 의미론으로 결합합니다.

동등한 필터는 동일하게 비교되고 직렬화되어야 합니다. 중복을 제거하고, 문자열과 연도를 정렬하며, Item에서는 `None`을 이름 있는 Item보다 앞에 두고, 종류는 `text`를 `table`보다 앞에 둡니다. 빈 문자열, 양수가 아닌 연도, 지원하지 않는 종류, 알 수 없는 차원은 유효하지 않습니다.

## 5. 결정론적 정렬

모든 전략은 다음 순서로 정렬한 결과를 공개해야 합니다.

1. 전략 점수 내림차순 2. `doc_id` 오름차순 3. `source_sha256` 오름차순 4. `start_char` 오름차순 5. `end_char` 오름차순 6. `chunk_id` 오름차순

정확한 벡터 SQL은 코사인 거리 오름차순으로 정렬한 다음, 이에 대응하는 출처 동점 판정 기준을 적용합니다. 메모리 내 `sort_hits()`는 새 목록을 반환하며 입력을 변경해서는 안 됩니다.

## 6. 벡터 검색

벡터 검색은 유한한 384차원 쿼리 벡터, 양수인 `k`, 공유 필터를 받습니다. null 임베딩을 제외하고 정확한 pgvector 코사인 거리를 사용해야 합니다. 반환되는 검색 결과의 점수는 `1 - cosine_distance`입니다.

M2는 HNSW 또는 IVFFlat 인덱스를 정의해서는 안 됩니다. 근사 인덱싱에는 M3의 지연 시간 및 재현율 근거가 필요합니다.

저수준 벡터 함수는 `k=0`일 때 데이터베이스에 접근하지 않고 빈 목록을 반환할 수 있지만, 프로덕션 하이브리드 서비스는 양수인 `k`를 요구합니다.

## 7. 어휘 검색

어휘 검색은 비어 있지 않은 쿼리, 양수인 `k`, 공유 필터를 받습니다. 쿼리를 SQL 값으로 바인딩하고 PostgreSQL `websearch_to_tsquery('english', query)`로 파싱해야 하며, 이것이 인젝션과 문법 오류에 대한 방어입니다. 파싱된 논리곱은 사용 전에 논리합으로 완화해야 합니다 — tsquery의 텍스트 표현에서 `&`를 `|`로 바꿔 `to_tsquery`로 다시 파싱합니다 — 자연어 질문의 모든 내용 어휘소를 요구하는 방식은 골든 스위트에서 recall@5 정확히 0을 측정했기 때문입니다. 인용 구문은 재작성을 거쳐도 `<->` 근접 의미를 유지합니다. 매칭과 순위는 같은 완화된 쿼리를 소비해야 하고, 생성된 `content_tsv`에 대해 `ts_rank_cd`를 정규화 `4 | 1` — extent 간 조화평균 거리와 `1 + log(length)`로 나누는, 측정에서 가장 좋았던 조합 — 로 실행해야 합니다. 기본값 0은 등장 횟수 세기로 퇴화해 역시 recall 0을 측정합니다.

반환되는 고유 점수는 PostgreSQL 범위 밀도 점수입니다. 문서와 코드는 이를 문자 그대로의 BM25라고 설명하거나 코사인 유사도와 수치로 비교해서는 안 됩니다. 이 어댑터 시그니처를 공유하는 별도의 BM25 실험군은 15절에서 명시합니다.

## 8. 융합과 재순위화

RRF는 `chunk_id`를 식별 키로 사용하고, 한 구성 요소 목록에서 처음 나온 항목 이후의 중복은 무시하며, 1부터 시작하는 각 구성 요소 순위에 대해 `1 / (rrf_k + rank)`를 더해야 합니다. `k`와 `rrf_k`는 모두 양수여야 합니다.

하이브리드 어댑터는 어휘 검색보다 벡터 검색을 먼저 기다려야 합니다. 각 구성 요소에서 `candidate_k`개의 후보를 요청하고 `candidate_k >= k`를 요구해야 합니다.

재순위화는 선택 사항입니다. 재순위화 공급자는 쿼리와 후보의 완전한 `index_text` 값을 받고, 후보마다 유한한 숫자형 점수를 하나씩 반환하며, 명시적인 실험군에서만 점수를 교체할 수 있습니다. 공급자가 없으면 결정론적인 출처 순서를 보존하고 `top_k`개로 잘라냅니다.

## 9. 프로덕션 서비스 결과

구성 요소 작업을 시작하기 전에 서비스는 빈 쿼리, 양수가 아닌 `k`, `candidate_k < k`, 양수가 아닌 `rrf_k`, 공급자/데이터베이스 차원 불일치를 거부해야 합니다. `candidate_k`를 생략하면 각 구성 요소에서 `max(20, 4 * k)`개의 후보를 요청해야 합니다. 명시적인 `candidate_k >= k` 값은 그대로 유지해야 합니다.

일반적인 `R&D` 약어는 쿼리 임베딩과 PostgreSQL FTS 모두에 전달하기 전에 `research development`로 확장해야 합니다. 이렇게 하면 두 구성 요소에서 쿼리의 의미가 일치합니다. CLI 응답에는 원래 사용자 쿼리를 유지할 수 있습니다.

벡터 및 어휘 어댑터는 호출자가 제공한 하나의 `AsyncSession`을 캡처하고 순차적으로 실행해야 합니다. 서비스는 다음 값을 반환합니다.

- `hits`: 변경할 수 없는 융합 `ChunkHit` 값
- `component_rankings.vector` 및 `component_rankings.lexical`: 변경할 수 없는 정렬된 청크 ID 튜플

구성 요소 순위에는 원시 구성 요소 점수가 들어가서는 안 됩니다. 융합 검색 결과에는 RRF 점수를 유지합니다. 이 값이 반환되는 융합 순서를 정의하기 때문입니다.

## 10. PostgreSQL 부트스트랩

새 스키마 부트스트랩은 하나의 엔진 트랜잭션에서 `CREATE EXTENSION IF NOT EXISTS vector`를 먼저 실행한 다음 `Base.metadata.create_all`을 호출해야 합니다. 반복 실행해도 안전해야 합니다.

이 도우미는 없는 객체만 생성합니다. 이전 스키마를 위한 마이그레이션으로 소개해서는 안 되며, 통합 테스트는 애플리케이션 스키마를 초기화하거나 잘라내서는 안 됩니다. 실제 테스트는 루프백 프로젝트 데이터베이스 URL만 허용하고, `localhost`를 `127.0.0.1`로 정규화하며, 연결 범위 임시 테이블을 사용해야 합니다. 제한된 연결 가능성 프로브와 검색 테스트는 하나의 이벤트 루프를 공유해야 합니다.

## 11. CLI 인수 경로

`python -m app.retrieval`은 `--query`를 필수로 요구하고, 양수인 결과 및 후보 제한을 받으며, 결정론적 임베딩 공급자 또는 OpenAI 임베딩 공급자를 선택하고, 선택적으로 null 임베딩을 채우며, 다음 항목이 포함된 JSON을 출력해야 합니다.

- 원래 쿼리와 공급자 이름
- 선택적인 임베딩 백필 개수
- 완전한 융합 검색 결과
- 벡터 및 어휘 청크 ID 순위

문서를 백필할 때 사용한 공급자는 쿼리를 임베딩할 때 사용하는 공급자와 일치해야 합니다.

## 12. 공개 표면과 정규 테스트 경로

`app.retrieval`은 공유 계약, 두 임베딩 공급자, 임베딩 백필, 벡터 및 어휘 검색, RRF와 하이브리드 검색, 재순위화, 서비스 결과 타입, `retrieve`를 공개해야 합니다.

테스트는 `app.retrieval`과 그 계층 모듈을 직접 가져옵니다. 빌드 가이드에 기록된 경로에 각 정규 파일을 생성합니다. 누락된 심볼에 의존하는 테스트는 `tests.support.need`를 통해 건너뛸 수 있지만, 완료 시 M2 테스트 모음을 직접 실행해 통과해야 합니다.

## 13. 완료 조건

- 모든 공급자 및 데이터베이스 경계에서 형태와 유한성을 검증합니다.
- 필터와 점수가 같은 모든 결과가 결정론적입니다.
- 벡터 SQL은 정확한 코사인 검색을 사용하며 근사 인덱스가 없습니다.
- 어휘 SQL은 원시 텍스트를 안전하게 구문 분석하고 범위 밀도 순위화를 사용합니다.
- RRF는 출처 점수 대신 순위를 사용합니다.
- 하나의 세션에서 벡터 및 어휘 구성 요소를 순차적으로 실행합니다.
- 구성 요소 순위에는 원시 점수 없이 ID만 공개합니다.
- 문자 그대로의 인수 쿼리는 인용이 포함된 NVDA FY2024 청크를 1위로 반환합니다.
- 결정론적 오프라인 테스트와 선택적인 실제 PostgreSQL 테스트가 통과합니다.
- 구성된 OpenAI 프로브가 유한한 구성 요소 384 개를 반환합니다.
- 집중형 및 전체 pytest, Ruff, 문서 동기화 검사가 통과합니다.

## 14. 향후 외부 검색 엔진 확장 경계

현재 기준선에서는 PostgreSQL이 `documents`와 `chunks`의 유일한 원본 저장소입니다. 9,172개 청크와 현재 요구 사항만으로 Elasticsearch 또는 OpenSearch를 추가하지 않습니다. 트래픽 증가 자체도 도입 근거가 아닙니다. PostgreSQL 쿼리와 인덱스를 조정한 뒤에도 측정된 `p95` 또는 `p99` 검색 지연 목표를 지키지 못하거나, 검색 부하를 독립적으로 확장해야 하거나, PostgreSQL FTS로 충족하기 어려운 분석기·동의어·오타 허용·하이라이트 기능이 필요할 때만 외부 검색 엔진을 후보로 검토합니다.

외부 검색 엔진을 도입하더라도 PostgreSQL은 원본 저장소로 남고, 외부 인덱스는 언제든 다시 만들 수 있는 검색용 복제본이어야 합니다. 각 검색 문서는 `chunk_id`, `source_sha256`, `start_char`, `end_char`, `index_text`와 검색 스키마 버전을 포함해야 합니다. 그래야 원본 청크와 외부 문서의 신원을 대조하고, 매핑이나 분석기가 바뀌었을 때 PostgreSQL에서 전체를 재색인할 수 있습니다.

애플리케이션 요청이 PostgreSQL과 외부 엔진에 직접 이중 쓰기해서는 안 됩니다. 커밋된 변경을 트랜잭셔널 outbox 또는 PostgreSQL 논리적 디코딩 기반 CDC로 내보내고, 소비자는 같은 변경을 다시 받아도 결과가 같도록 멱등하게 적용해야 합니다. PostgreSQL 트랜잭션은 외부 엔진까지 묶을 수 없으므로 현재의 단일 세션 스냅샷 보장은 시스템 간 최종 일관성 경계로 바뀝니다. 따라서 허용 가능한 최대 동기화 지연을 먼저 정하고, 지연·실패·누락 문서 수를 운영 지표로 감시해야 합니다.

도입 순서는 다음과 같습니다.

1. 현재 PostgreSQL의 검색 품질과 지연 시간 기준선을 기록합니다. 2. 버전이 붙은 외부 인덱스를 만들고 PostgreSQL 원본에서 전체 백필합니다. 3. 변경 스트림을 연결하고 동기화 지연과 실패를 감시합니다. 4. 실제 요청을 두 검색 경로에 그림자 실행하여 결과, 재현율, 지연 시간을 비교합니다. 5. 검증을 통과한 인덱스로 alias를 원자적으로 전환하되 PostgreSQL 폴백을 유지합니다.

기존 경계는 이 전환의 일부만 준비합니다. 외부 검색 어댑터도 `RetrievalFilters`를 받아 `ChunkHit`을 반환해야 하므로 `rrf_fuse`와 공개 `retrieve` 응답 계약은 유지할 수 있습니다. 그러나 현재 M2에는 외부 엔진 어댑터, 동기화 작업자, 지연 감시, 재색인 또는 전환 코드가 없습니다. 실제 도입 여부는 M3와 운영 환경의 측정 결과로 결정합니다.

## 15. 유예된 BM25 어휘 순위 실험군

1절부터 14절까지는 M2.1부터 M2.8까지의 기준선을 정의합니다. 이 기준선에는 BM25 구현이 없으며, 어떤 문서도 이를 BM25로 제시해서는 안 됩니다.

그럼에도 BM25는 여전히 필요합니다. 필수 어휘 기준선 요구사항은 BM25 또는 TF-IDF를 지목하는데 범위 밀도 순위는 그 어느 쪽도 아닙니다. M2.9는 기준선을 완료한 뒤 직접 작성한 BM25 순위 실험군을 추가해야 합니다.

이 실험군은 어휘 어댑터 시그니처를 재사용하고 `ChunkHit`을 반환해야 하며, 그래야 `rrf_fuse`와 공개 `retrieve` 계약이 변하지 않습니다. 모든 통계는 생성 열 `content_tsv`에서 파생해야 하고, 이 열은 `ts_rank_cd`가 이미 순위를 매기는 대상입니다. 그러면 두 실험군이 하나의 토크나이저, 하나의 어간 추출기, 하나의 불용어 목록을 공유하므로 순위 함수만이 둘 사이의 유일한 변수로 남습니다.

저장된 tsvector가 필요한 통계를 제공합니다. `unnest(content_tsv)`는 각 어휘소와 그 단어 빈도인 `cardinality(positions)`를 산출하고, 문서 빈도는 일치하는 청크 행의 개수이며, 문서 길이는 한 청크의 단어 빈도 합계입니다. 영속화한 단어 통계는 `chunks`만으로 재구축할 수 있어야 하고, 기존 열을 수정해서는 안 되며, 골든 범위를 변경해서도 안 됩니다. 여기에는 확장도 외부 검색 엔진도 필요하지 않습니다.

채점 함수는 `k1`과 `b`를 내장 상수가 아니라 명시적 매개변수로 받아야 합니다. `b`를 0으로 두면 길이 정규화가 꺼지고 그 기여도가 분리됩니다. 이 구성은 TF-IDF가 아니며 그렇게 라벨해서도 안 됩니다. 확률형 IDF 항이 다르기 때문입니다.

IDF 항은 공표된 두 변형 중에서 고를 수 있어야 합니다. Robertson의 `ln((N - df + 0.5) / (df + 0.5))`는 코퍼스 절반 이상이 가진 어휘소에서 음수가 되어 매칭할 때마다 점수를 깎고, 이 규모의 코퍼스에서는 순위를 뒤집습니다. Lucene의 `ln(1 + ...)`은 하한이 0입니다. 따라서 기본값은 `lucene`이어야 하고, 차이가 측정 가능하므로 `robertson`도 선택 가능한 상태로 남아야 합니다. 문서 빈도는 코퍼스 크기로 클램프해서, 청크 삭제로 낡아진 통계가 로그를 정의되지 않게 만들 수 없어야 합니다.

순위 함수와 그 상수, IDF 변형은 설정에서 도달할 수 있어야 하고 명령 하나에 한해 덮어쓸 수 있어야 합니다. 파생 term 통계는 청크 집합이 바뀔 때마다 명시적 명령으로 재구축해야 하며, 질의마다 암묵적으로 재구축해서는 안 됩니다.

단위 테스트는 손으로 계산한 고정값을 기준으로 공식을 검증해야 합니다. 검증되지 않은 순위 함수는 순위 함수가 없는 것보다 나쁜 근거입니다. 최소한 하나의 테스트는 살아 있는 PostgreSQL 코퍼스에 SQL을 실행해 독립적인 Python 참조 구현과 일치할 것을 요구해야 합니다. 실행되는 구문이 곧 BM25를 계산하는 구문은 아니기 때문입니다.

M2.9는 프로덕션 어휘 랭커를 선택해서는 안 됩니다. 두 실험군은 모두 M3.4 어블레이션 실험 행렬에 들어가며, 문서화된 기본값은 측정된 재현율, MRR, 지연 시간을 따릅니다.

## 16. 유예된 로컬 모델 공급자

1절부터 15절까지는 머신러닝 의존성이 없는 시스템을 서술합니다. 임베딩은 API나 토큰 해싱에서 나오고 재순위화 경계에는 구현이 없습니다. M2.10과 M2.11이 이를 바꾸며, 둘 다 기본 설치에 포함되지 않습니다.

torch 백엔드는 정확히 하나만 설치되도록 상호 배타적인 extra로 선언해야 하고, `app.retrieval`을 import하는 데 그중 무엇도 필요해서는 안 됩니다. 두 공급자 모두 모델 라이브러리를 처음 필요로 하는 호출 안에서 import해야 하며, 공급자를 생성하는 것만으로 가중치를 읽어서는 안 됩니다.

M2.10은 `EmbeddingProvider` 뒤에 로컬 sentence-transformer를 추가해야 합니다. 기본 모델은 정확히 `DIM` 차원을 만들어 도입에 마이그레이션이 필요 없어야 하고, 폭이 다른 모델은 벡터를 저장하기 전에 거부해야 합니다. 자체 검증을 새로 만들지 않고 기존 출력 검증을 재사용해야 합니다.

M2.11은 `RerankProvider` 뒤에 cross-encoder를 추가해야 합니다. 점수는 범위가 없는 로짓이며 어떤 범위로 제한하거나 코사인 유사도 또는 BM25와 비교해서는 안 됩니다.

프로덕션 서비스는 선택적 리랭커를 받아야 합니다. 넘기지 않으면 동작이 M2.7과 동일해야 합니다. 넘기면 융합이 후보 묶음 전체를 유지하고 리랭커가 `k`로 줄여야 합니다. 리랭커에게 `k`개만 건네는 것은 이 단계의 목적을 무산시킵니다. 구성 요소 순위는 각 검색기가 제안한 것을 계속 기록해야 합니다.

두 공급자 모두 동기이고 연산 위주인 모델을 돌리므로 이벤트 루프 바깥에서 실행해야 합니다.

M2.10과 M2.11은 프로덕션 기본값을 선택해서는 안 됩니다. 재순위화는 호출자가 켜지 않는 한 꺼져 있고, M3.4가 측정된 재현율, MRR, 지연 시간으로 결정합니다.
