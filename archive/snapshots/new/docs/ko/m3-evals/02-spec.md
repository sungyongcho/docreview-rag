# M3 명세

## 1. 범위

이 명세는 엄격한 골든 데이터, 결정론적 채점, 타입이 지정된 회귀 비교, 평가 결과 영속화, 구성 가능한 검색 어블레이션 실험, 사례별 원시 산출물, 측정된 지연 시간 예산으로 이루어진 전체 M3 경로를 정의합니다. 계층은 M3.1 골든, M3.2 채점, M3.3 회귀, M3.4 어블레이션 실험과 러너 순서로 구축해야 합니다.

정규 데이터 세트는 `data/golden/retrieval.json`입니다. 작성자 승인을 기다리는 에이전트 선별 후보 28 개를 포함합니다. 커밋된 사례 중 사람이 검증한 사례는 없습니다.

## 2. 안정적인 원문 계약

양성 답변은 원시 원문의 반개구간 `[start_char, end_char)`이며, `doc_id`와 `source_sha256`으로 식별되는 정확한 UTF-8 공시 자료 안에 있습니다. 오프셋은 바이트, 렌더링된 텍스트, 파서 블록, 청크 본문, 데이터베이스 청크 ID가 아니라 디코딩된 유니코드 문자를 가리킵니다.

골든 답변은 특정 청킹 구성과 독립적으로 유지되어야 합니다. 따라서 현재 데이터 세트는 답변이 포함된 원문 문장, 단편 또는 표 행만 인용합니다. 어블레이션 실험에 따라 검색된 청크는 달라질 수 있지만 원시 답변 범위는 안정적으로 유지됩니다.

모든 양성 범위는 다음 조건을 모두 충족해야 합니다.

1. 해당 문서가 `data/corpus/manifest.json`에 존재해야 합니다. 2. 해당 SHA-256 값이 정확한 원문 파일 바이트 해시와 같아야 합니다. 3. `0 <= start_char < end_char <= len(decoded_source)`를 충족해야 합니다. 4. 인용 범위에 눈으로 확인할 수 있는 원문 증거가 있어야 합니다. 5. 해당 식별자가 사례나 커밋된 스위트 안에서 중복되지 않아야 합니다.

## 3. JSON 스키마

파일 루트는 JSON 배열입니다. 알 수 없는 필드, 중복 JSON 객체 키, 중복 사례 ID, 정규화 후 중복되는 질문, 유효하지 않은 열거형, 스칼라 강제 변환, 빈 텍스트 필드, 중복 태그, 잘못된 형식의 해시, 유효하지 않은 범위는 오류입니다.

각 사례의 형태는 다음과 같습니다.

```json
{
  "id": "m3c-07",
  "question": "What was AMD's research and development expense in fiscal 2023?",
  "category": "exact_number",
  "facet": "numeric",
  "tags": ["demo-hero"],
  "answers": [
    {
      "doc_id": "AMD-FY2023",
      "source_sha256": "0e9d83bd98b81b70050a88635171e721488f783eada9686fe21d6919ee1b668e",
      "start_char": 756006,
      "end_char": 756419
    }
  ],
  "expected_label": "SUPPORTED",
  "reference_answer": "$5.872 billion.",
  "note": "Exact-number retrieval from a multi-year financial statement table.",
  "curation_status": "agent-curated",
  "approval_status": "pending-author-approval",
  "human_verified": false
}
```

### 범주와 관점

`category`는 규범적인 M3 평가 범주입니다.

- `simple_lookup`
- `exact_number`
- `multi_hop`
- `absent`

`facet`은 별도로 필요한 의미 검토 차원입니다.

- `factual`
- `comparison`
- `risk`
- `policy`
- `numeric`

두 차원을 하나로 합치면 안 됩니다. 현재 세트는 인위적으로 균등하다고 주장하는 대신 정확한 분포를 의도적으로 기록합니다. 범주는 단순 조회 13개, 정확한 수치 사례 다섯 개, 다중 홉 사례 여섯 개, 부재 사례 네 개이며, 관점은 사실 여섯 개, 비교 여섯 개, 위험 여섯 개, 정책 다섯 개, 수치 다섯 개입니다.

### 양성 및 부재 불변 조건

부재가 아닌 사례에는 검증된 답변 범위가 하나 이상 있어야 하고 `SUPPORTED`를 예상해야 하며 근거가 있는 참조 답변을 제공해야 합니다. 부재 사례에는 범위가 없어야 하고 `NOT_IN_DOCS`를 예상해야 하며 참조 답변으로 `NOT_IN_DOCS`를 사용해야 합니다.

작성자가 별도 검토를 수행하고 기록하기 전까지 모든 사례는 `curation_status="agent-curated"`, `approval_status="pending-author-approval"`, 리터럴 JSON 불리언 `human_verified=false`를 사용해야 합니다. 기계 검증을 사람의 검증으로 표현해서는 안 됩니다.

## 4. 데이터 세트 구성

커밋된 세트에는 양성 사례 24 개와 부재 사례 네 개가 있습니다. 양성 사례는 공시 자료 20 개를 모두 인용하며 티커별 사례 여섯 개로 균형을 이룹니다. 양성 `demo-hero` 사례 여덟 개는 티커별 두 개로 균형을 이룹니다.

중복되는 비히어로 양성 후보 4개를 음성 가드레일 사례로 교체하여 규범적 범주 차원에 정직한 부재 동작을 포함했습니다. 음성 사례는 원문 범위를 인용하는 것이 아니라 변경 불가능한 전체 코퍼스에 관한 주장이며, 작성자 확인을 기다리고 있습니다.

## 5. 로더 동작

`load_golden_cases()`는 JSON 파일 하나 또는 `*.json` 파일을 파일명 순서로 병합하는 디렉터리를 받습니다. 스키마, 사례 간 고유성, 코퍼스 매니페스트, 원문 해시, 경계, 눈으로 확인할 수 있는 증거 검증이 성공한 뒤에만 `list[GoldenCase]`를 반환합니다. 조건을 하나라도 위반하면 `GoldenDataError`가 발생합니다. 로더는 유효하지 않은 사례를 건너뛰거나, 복구하거나, 정규화하거나, 조용히 버리지 않습니다.

`validate_golden_sources()`는 이미 타입이 지정된 사례를 가진 호출자가 코퍼스 결합 검사를 독립적으로 사용할 수 있게 합니다. 원문 파일은 바이트로 읽고 범용 줄바꿈 변환 없이 UTF-8 형식으로 디코딩하며, 원본 바이트로 해시하고 디코딩된 문자 오프셋으로 색인합니다.

## 7. 검토 및 완료 게이트

기계 게이트를 통과하려면 집중 테스트, Ruff, 문서 동기화가 성공해야 합니다. 사람의 승인은 `data/golden/REVIEW.md`에 설명된 별도 게이트이며 테스트 통과로 충족되지 않습니다. 작성자가 해당 검토를 마칠 때까지 모든 사례는 에이전트가 선별한 후보로 유지되며 사람이 검증했다는 주장은 허용되지 않습니다.

## 8. 결정론적 검색 채점

`app.evals.scoring`은 양성 골든 사례만 평가합니다. 부재 사례에는 검색 범위가 없으며 이후 레이블 정확도 채점을 위해 남겨 둡니다. 빈 골든 범위 목록을 `score_case()`에 전달하면 오류가 발생합니다.

### 반개구간 범위 관련성

단일 관련성 임곗값은 `IOU_THRESHOLD=0.05`입니다. 골든 범위 `a`와 검색된 청크 `b`는 `doc_id`와 `source_sha256`가 모두 일치할 때만 비교할 수 있습니다. 비교 가능한 범위의 계산식은 다음과 같습니다.

```text
overlap = max(0, min(a.end_char, b.end_char) - max(a.start_char, b.start_char))
union = (a.end_char - a.start_char) + (b.end_char - b.start_char) - overlap
IoU = overlap / union
relevant = IoU >= IOU_THRESHOLD
```

경계만 맞닿는 반개구간은 서로 겹치지 않습니다. 의도적으로 낮은 임곗값을 사용하여 서로 다른 청킹 구성이 동일한 좁은 원시 답변을 포함할 때 청크 경계가 같지 않아도 인정합니다. 스냅샷 해시 대조는 오래된 오프셋이 점수를 받지 못하게 합니다.

### 사례별 대조

처음 `k`개 검색 결과만 고려하며 `k`는 양의 정수여야 합니다. 재현율은 관련 검색 결과가 하나 이상 포함한 고유 골든 범위의 수를 집계합니다. 동일한 골든 범위를 포함하는 반복 검색 결과는 재현율을 높이지 않습니다. 넓은 검색 결과 하나가 각 범위의 IoU 임곗값에 독립적으로 도달하면 서로 다른 골든 범위를 여러 개 포함할 수 있습니다.

`CaseScore`는 골든 범위 수와 일치 수, `recall_at_k`, 이진 `hit_at_k`, 처음 관련 결과의 일부터 시작하는 순위와 그 역수를 기록합니다. 상위 k개에 관련 검색 결과가 없는 사례는 세 지표 값이 모두 0이며 첫 관련 순위도 없습니다.

### 스위트 지표

`recall_at_k()`는 사례별 재현율의 산술 평균인 매크로 재현율입니다. 따라서 사례마다 골든 범위 수가 달라도 각 질문의 가중치는 같습니다. `hit_rate_at_k()`는 상위 k개 안에 관련 검색 결과가 하나라도 있는 사례의 비율입니다. MRR은 각 사례에서 첫 관련 결과 순위 역수의 산술 평균이며 `mrr()`과 `mean_reciprocal_rank()`로 모두 노출됩니다. 스위트는 비어 있지 않아야 하고, 고유한 사례 ID를 사용하며, 공통된 하나의 `k`를 사용해야 합니다.

`score_suite()`는 이 세 지표와 사례 ID순으로 정렬한 사례별 결과를 반환합니다. 대조는 변경 불가능한 원문 식별자와 반개구간 좌표에만 의존하고 데이터베이스 청크 ID나 파서 순번에는 절대 의존하지 않습니다. 따라서 순위가 지정된 원문 포함 범위가 같다면 다시 청킹하거나 청크 식별자 순서를 바꾸어도 결과가 달라지지 않습니다.

정규 채점 테스트를 직접 실행합니다.

```bash

```

## 9. 회귀 비교와 영속화

회귀 게이트는 명시적으로 클수록 좋은 지표인 `recall_at_k`, `hit_rate_at_k`, `mrr`에만 이 안정적인 순서로 적용됩니다. 각 지표에는 구성 가능한 최대 절대 하락폭이 있습니다. 허용 오차와 같은 하락은 통과하고 더 큰 하락은 실패합니다. 지연 시간 같은 추가 값은 저장하지만 암묵적인 방향을 부여하지 않습니다.

실험 구성은 문자열 키를 가진 유한 JSON 객체여야 합니다. 정규 직렬화는 정렬된 키, 간결한 구분자, UTF-8 문자를 사용하며 NaN이나 무한대를 허용하지 않습니다. 두 구성은 정규 JSON 값과 스위트 이름이 일치할 때만 비교할 수 있습니다.

`EvalResult`는 스위트 하나, 정규 구성, 지표 객체, 원시 산출물 경로, 시간대 정보가 있는 타임스탬프를 영속화합니다. `latest_comparable_baseline()`은 일치하는 행을 타임스탬프, 그다음 ID 기준으로 최신 항목부터 정렬합니다. 영속화 과정은 커밋하지 않고 플러시하며 트랜잭션 소유권은 호출자에게 있습니다.

정규 회귀 테스트를 직접 실행합니다.

```bash
uv run pytest tests/evals/test_03_regression.py -v
```

## 10. 어블레이션 실험 행렬

`ExperimentConfig`는 비교 가능성에 영향을 미치는 모든 변수를 명시해야 합니다.

- 구조 인식 청킹 목표와 원시 범위 골든 식별자
- 어휘, 벡터 또는 하이브리드 검색 전략
- 어휘 순위 함수. `ts_rank_cd` 또는 명시적인 `k1`, `b`, IDF 변형을 받는 직접 작성한 BM25
- `k`, 구성 요소 후보 깊이, RRF 상수
- 임베딩 공급자와 차원, 그리고 그것이 호스팅형인지 로컬인지
- 리랭커는 이 결정론적 M3 기준선에서 사용하지 않는다. cross-encoder는 별도 승인한 후속 실험에서 후보 깊이와 함께 기록한다
- 격리 환경, 유료 호출 플래그, 채워진 임베딩 변경 플래그

기본 행렬은 청크 목표 500 및 1200에 어휘, 벡터, 하이브리드 검색을 교차하고, 어휘 질의를 실제로 던지는 전략은 모두 두 어휘 순위 함수로 확장합니다. 벡터 검색은 어휘 질의를 던지지 않으므로 순위 함수마다가 아니라 청크 목표마다 실험군 하나를 기여하고, 그래서 기본 행렬은 열두 개가 아니라 열 개입니다. 모든 실험군은 자신의 순위 함수를 구성 이름과 artifact 파일명과 구성 provenance에 기록해야 합니다. 순위 함수만 다른 두 실행이 서로를 덮어쓰지도, 나중에 혼동되지도 않게 하기 위해서입니다. BM25 통계는 특정 청킹의 성질이므로 임시 코퍼스 실험군마다 정확히 한 번, 적재 중에 그리고 어떤 실험이 돌기 전에 재구축해야 합니다. 청크 목표를 가로질러 공유한 재구축은 어느 쪽도 묘사하지 못합니다. 질의 예산은 자신이 측정한 순위 함수를 명시해야 합니다. M2.11 cross-encoder는 현재 10개 기준선에 자동으로 추가하지 않으며, 품질·지연·후보 깊이를 별도 승인한 후속 실험에서 측정합니다. 구성 이름은 고유한 소문자 케밥 표기법을 사용하고 결과는 청크 목표, 전략 순서, 어휘 순위 함수, 이름으로 정렬합니다. 다시 청킹할 때 골든 범위를 절대 수정해서는 안 됩니다.

정규 어블레이션 테스트를 직접 실행합니다.

```bash
uv run pytest tests/evals/test_04_ablation.py -v
```

## 11. 러너와 원시 산출물

러너는 사례 ID순으로 전체 28개 사례를 평가합니다. 모든 사례의 원시 검색 결과와 지연 시간을 기록하지만 검색 품질 지표는 원문 범위를 포함한 24개 사례에 대해서만 계산합니다. 부재 사례 네 개에는 향후 레이블 정확도 계약이 필요하며 M3 원시 산출물에서 `score=null`이어야 합니다.

모든 실험 산출물은 다음 내용을 포함합니다.

- 스키마 버전, 스위트, UTC 타임스탬프, 완전한 실험 구성
- 전체 수, 채점된 양성 수, 채점되지 않은 부재 수
- 리터럴 골든 검토 출처
- Recall@k, Hit Rate@k, MRR, 지연 시간 요약
- 각 완전한 골든 사례, 순위가 있는 원시 검색 결과 목록, 지연 시간, 선택적인 양성 사례 점수

산출물 JSON은 안정적인 UTF-8 형식이고 키가 정렬된 유한 JSON이어야 합니다. 파일명은 UTC 실행 타임스탬프 뒤에 고유한 구성 이름을 붙입니다. 원시 산출물이 없는 지표는 허용 가능한 증거가 아닙니다.

정규 러너 테스트를 직접 실행합니다.

```bash
uv run pytest tests/evals/test_05_runner.py -v
```

## 12. 격리와 예산

각 청킹 실험군은 전용 연결의 임시 PostgreSQL 테이블에 구축합니다. 타이머는 매니페스트 로드, 파싱, 청크 구성 전에 시작하고 임시 영속화, GIN 구성, 임베딩 백필이 끝난 후 종료합니다. 연결을 닫으면 실험 코퍼스가 폐기됩니다. 러너는 기존 벡터에서 공급자 식별 정보를 읽거나, 채워진 임베딩을 덮어쓰거나, 공급자 공간을 혼합해서는 안 됩니다.

인수 예산은 다음과 같습니다.

- 최대 300 벽시계 초 안에 완전한 문서 20개 색인 실험군 하나 처리
- 최대 90 벽시계 초 안에 순차 검색 쿼리 200개 처리

예산 산출물은 개수, 공급자 식별 정보, 관측된 지속 시간, 임곗값, 통과 상태, 환경 식별 정보, 유료 호출 상태, 채워진 코퍼스 변경 상태를 저장해야 합니다. 이는 측정 결과이므로 대체값이나 조작한 값은 금지됩니다.

## 13. 공급자 및 검토 출처

기본 인수 경로는 `provider=deterministic`을 사용합니다. 이 공급자의 토큰 해시 벡터는 안정적인 오프라인 기준선을 제공하지만 의미 품질을 대신하지는 않습니다. OpenAI 실행은 작성자의 비용 승인, 유효한 자격 증명, 모델 접근 권한이 필요한 명시적 옵트인입니다. 별도 산출물 세트를 작성해야 하며 여전히 임시 코퍼스 테이블을 사용해야 합니다.

골든 검토 출처와 임베딩 공급자 출처는 서로 독립적입니다. 결정론적 실행으로 기존 벡터를 생성한 공급자를 확인할 수 없으며, 기계 테스트를 거친 골든 데이터도 에이전트가 선별하고 작성자 승인을 기다리는 상태로 유지됩니다.
