# M1.4 버그

각 항목은 증상, 근본 원인, 수정, 회귀 방지책을 기록한다.

## B01 — 재실행 시 청크 중복

상태: 수정 완료.

증상: 같은 코퍼스를 두 번 삽입하면 청크 행이 두 배가 될 수 있었다.

근본 원인: 일반 삽입문은 모델에 이미 있는 결정론적 식별 정보를 표현하지 못했다.

수정: `(doc_id, ordinal)`을 키로 삼은 PostgreSQL 충돌 업데이트를 사용하고 이름이 지정된 고유 제약 조건을 유지한다.

회귀 검증: `test_chunk_upsert_targets_doc_ordinal_and_never_writes_embeddings`.

## B02 — 재청킹 후 검색 가능한 유령 행 잔존

상태: 수정 완료.

증상: 청크 수가 (500)에서 (480)으로 바뀐 문서에 이전 행(480)부터 (499)까지가 남아 있었다.

근본 원인: 업서트는 기존 키를 업데이트하고 새 키를 삽입하지만, 어떤 이전 키가 더 이상 입력에 포함되지 않는지는 추론할 수 없다.

수정: 빈틈없는 ordinal을 요구하고 같은 트랜잭션 안에서 `ordinal >= current_count`를 삭제한다.

회귀 검증: 트랜잭션 명령문 수 테스트와 PostgreSQL 개수 검사.

## B03 — 합성 문맥과 증거를 구분할 수 없음

상태: 수정 완료.

증상: 하위 인용에서 문장이 공시에서 왔는지 반복된 검색 헤더에서 왔는지 구분할 수 없었다.

근본 원인: 이전 스키마는 결합된 `content` 값 하나만 저장했다.

수정: `body`, `context_header`, `index_text`를 영속화하고 `content`는 별칭으로만 유지한다.

회귀 검증: `test_filing_records_keep_body_context_index_text_and_metadata`.

## B04 — 소스 구간이 해당 스냅샷보다 오래 남을 수 있음

상태: 수정 완료.

증상: 유효해 보이는 오프셋이 교체된 소스 바이트에 적용될 수 있었다.

근본 원인: 문서 행이 소스 길이나 해시를 식별하지 않았다.

수정: 문서에 소스 길이와 SHA-256 값을 영속화하고, 청크에 해시를 반복해 저장하며, 쓰기 전에 그 관계를 검증한다.

회귀 검증: `test_02_records.py`의 매개변수화된 출처 추적 실패 사례.

## B05 — 단일 대량 명령문의 매개변수 초과 위험

상태: 수정 완료.

증상: 전체 코퍼스 삽입이 드라이버 한도를 넘거나 매우 큰 SQL 명령문을 할당할 수 있었다.

근본 원인: 수천 개의 행을 하나의 values 절로 처리했다.

수정: 코퍼스 트랜잭션 안에서 크기(500)의 결정론적 청크 배치를 실행한다.

회귀 검증: `test_persist_seed_batch_owns_one_transaction_and_batches_chunks`.

## B06 — 문서 하나 이후의 실패로 일부 코퍼스 생성

상태: 수정 완료.

증상: 이후 청크 명령문이 실패해도 앞선 행이 커밋될 수 있었다.

근본 원인: 트랜잭션 소유권이 암묵적이거나 문서별로 나뉘어 있었다.

수정: 먼저 준비한 다음 문서, 청크, 오래된 행 정리를 아우르는 명시적 트랜잭션 하나를 소유한다. 이미 트랜잭션이 있는 세션은 거부한다.

회귀 검증: `test_03_upserts.py`의 롤백 및 중첩 트랜잭션 테스트.

## B07 — 텍스트가 바뀌었지만 이전 임베딩은 유지됨

상태: 통합 검토 후 수정 완료.

증상: 충돌 업데이트가 `index_text`를 교체했지만 이전 텍스트에서 계산된 임베딩은 남겼다. 벡터 검색이 의미상 오래된 결과를 반환할 수 있었다.

근본 원인: 업데이트에서 `embedding`을 제외하면 인덱스 입력이 바뀌어도 저장된 값이 항상 보존된다.

수정: PostgreSQL `CASE`로 임베딩을 할당한다. `index_text`가 같으면 보존하고, 그렇지 않으면 `NULL`로 설정한다. M1.4 단계는 여전히 벡터를 생성하지 않는다.

회귀 검증: `test_chunk_upsert_invalidates_only_stale_embeddings`와 선택적 실제 PostgreSQL 보존/무효화 연습.

## B08 — 스키마 생성을 마이그레이션으로 오해

상태: 문서화된 한계.

증상: 이전 테이블이 있는 데이터베이스에서 `create_all`을 실행하면 누락된 열이 그대로 남는다.

근본 원인: SQLAlchemy 메타데이터 생성은 누락된 테이블을 추가할 뿐 변경 계획을 세우지 않는다.

수정: 스키마 생성을 명시적 동의 방식으로 만들고 새 스키마 부트스트랩 전용이라고 설명한다. 기존 스키마에는 검토된 마이그레이션이나 일회용 초기화를 사용한다.

회귀 검증: 명령 도움말과 이 문서화된 경계.
