# M1.4 명세

## 1. 범위

M1.4 단계는 저장소에서 파싱한 공시(20) 코퍼스와 현재 M1.3 청크 전체를 PostgreSQL 행으로 변환해야 한다. 결정론적 재실행 동작을 유지하면서 소스 출처 추적 정보, 문서 메타데이터, 검색 텍스트, 표 종류를 영속화해야 한다.

M1.4 단계는 임베딩을 생성하거나, 임베딩 모델을 선택하거나, 임베딩 공급자를 호출하거나, 검색을 구현해서는 안 된다.

## 2. 문서 스키마

`documents.doc_id`가 기본 키다. 각 행에는 다음 항목이 있어야 한다.

- `ticker`, 숫자형 `cik`, `fiscal_year`, `form`
- `filing_date`, `report_period`, `accession`, 소스 `url`
- `parse_status`: `parsed` 또는 `needs_profile_update`만 허용
- 원본 xref 항목, Item별 상태, 참조 소스를 담은 `item_index` JSON
- 양수 `source_length`
- 소문자 16진수 `source_sha256`(길이: 64)

해시는 정확한 소스 스냅샷을 식별한다. 길이는 기준 디코딩 Python 문자열에서 청크 좌표의 범위를 제한하며, 좌표는 UTF-8 바이트 오프셋이 아니다.

제목 기반 공시에서는 `item_index`가 비어 있을 수 있다. xref 공시에서는 상태가 `empty_disclosure` 또는 `incorporated_by_reference`여서 M1.3 단계가 청크를 만들 소스 본문이 없는 Item에 대한 증거가 된다.

## 3. 청크 스키마

`chunks.id`는 대리 기본 키다. `(doc_id, ordinal)`은 결정론적 업서트 키다. 각 행에는 다음 항목이 있어야 한다.

- null을 허용하는 SEC `item`
- `kind`: `text` 또는 `table`만 허용
- 음이 아니고 빈틈없는 `ordinal`
- 비어 있지 않은 소스 파생 `body`
- 비어 있을 수 있는 합성 `context_header`
- `index_text`: M1.3 청크 `content`와 같음
- `start_char`, `end_char`, `source_sha256`
- 사람이 읽을 수 있는 `citation`
- null을 허용하는 `embedding`
- 생성된 `content_tsv`: `index_text`를 바탕으로 함

구간은 반개방이며 `0 <= start_char < end_char <= documents.source_length`를 만족해야 한다. 청크 해시는 해당 문서 해시와 같아야 한다. `content`는 `index_text`의 ORM 별칭이며 중복된 데이터베이스 열이 아니다.

## 4. 결정론적 레코드 변환

고정된 매니페스트, 파서 구현, 청크 구현, 소스 스냅샷에 대해 레코드 변환은 같은 불변 레코드를 같은 순서로 만들어야 한다.

준비 단계는 다음을 수행해야 한다.

1. 파싱 전에 예상 매니페스트 수를 검증한다. 2. 매니페스트 항목을 티커와 보고일로 정렬한다. 3. 모든 항목을 파싱하고 청킹한다. 4. 문서 메타데이터와 소스 식별 정보를 검증한다. 5. 모든 청크를 해당 문서에 맞춰 검증한다. 6. 문서는 `doc_id`로, 청크는 `(doc_id, ordinal)`로 정렬한다. 7. 중복 문서, 알 수 없는 청크 문서, 중복 키, 빈틈이 있는 ordinal을 거부한다.

준비 중에는 데이터베이스 트랜잭션을 열어 두어서는 안 된다.

## 5. PostgreSQL 업서트

문서 명령문은 다음을 사용해야 한다.

```sql
ON CONFLICT (doc_id) DO UPDATE
```

청크 명령문은 다음을 사용해야 한다.

```sql
ON CONFLICT (doc_id, ordinal) DO UPDATE
```

두 명령문은 변경 가능한 모든 영속 입력 필드를 업데이트해야 한다. 청크 삽입과 레코드 딕셔너리는 `embedding`과 `content_tsv`를 제외해야 한다. M1.4 단계는 임베딩을 생성하지 않고 PostgreSQL이 검색 벡터를 계산하기 때문이다.

임베딩 충돌 할당은 다음 진리표를 따라야 한다.

| 저장된 `index_text`와 새 `index_text`의 일치 여부 | 결과 임베딩 |
|---|---|
| 예 | `NULL`을 포함한 저장값 보존 |
| 아니요 | `NULL`로 설정 |

이는 M1.4 단계와 M2 사이의 캐시 무효화 경계다. M2는 시드 트랜잭션이 커밋된 뒤 null 임베딩을 채울 수 있다.

## 6. 트랜잭션 의미

`persist_seed_batch()`는 전체 배치에 대한 트랜잭션 하나를 소유한다. 호출자는 활성 트랜잭션이 없는 `AsyncSession`을 제공해야 한다. 작업 순서는 다음과 같다.

1. 모든 문서 행을 업서트한다. 2. 청크 행을 제한된 배치로 업서트한다. 3. 포함된 모든 문서에서 오래된 후행 ordinal을 제거한다. 4. 문맥이 정상 종료되면 커밋한다.

검증, SQL, 연결 또는 제약 조건 오류는 밖으로 전파되어 롤백을 일으켜야 한다. 함수는 트랜잭션 문맥 밖에서 `commit()` 또는 `rollback()`을 호출해서는 안 된다.

빈 문서 배치는 유효하며 아무것도 쓰지 않는다. 양수가 아닌 청크 배치 크기는 유효하지 않다.

## 7. 오래된 행 정책

ordinal은 0부터 빈틈없이 이어지는지 검증하므로 문서의 현재 유효 집합은 `[0, chunk_count)`다. 업서트 후 해당 문서에서 `ordinal >= chunk_count`인 행을 삭제해야 한다. 입력 배치에 없는 문서의 행은 작업 범위 밖이므로 삭제해서는 안 된다.

## 8. 스키마 수명 주기

명령은 SQLAlchemy `create_all`을 호출할 수 있지만 `--create-schema`를 명시해야 한다. 이 기능은 누락된 테이블과 인덱스를 만들 수 있지만 마이그레이션 메커니즘으로 제시해서는 안 된다. 이전 스키마가 설치되어 있으면 검토된 마이그레이션이나 새 일회용 데이터베이스를 사용해야 한다.

## 9. 완료 게이트

- 준비된 문서 레코드가 정확히 (20)개이며 골든 문서 식별 정보와 일치한다.
- 준비된 청크 합계가 표 청크를 포함한 현재 M1.3 골든 데이터와 일치한다.
- 모델, 변환, 명령문, 트랜잭션, 정규 패키지 테스트가 DB 없이 통과한다.
- PostgreSQL을 사용할 수 없으면 선택적 테스트가 문제없이 건너뛴다.
- PostgreSQL을 사용할 수 있으면 동일한 쓰기를 두 번 실행해도 행 수가 안정적으로 유지된다.
- 같은 텍스트로 재실행하면 기존 임베딩을 보존하고, 텍스트가 바뀌면 이를 비운다.
- 모든 M1.4 Python 파일에서 Ruff가 통과한다.
