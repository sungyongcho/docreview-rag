# 실패 분석

이 시스템은 실패의 가시성을 제품의 일부로 취급한다. 올바른 결과는 유창한 답변이 아니라 검사할 수 있는 거부 또는 `NOT_IN_DOCS`인 경우가 많다.

## 실패 매트릭스

| 경계 | 실패 | 감지 | 시스템 동작 | 남는 트레이드오프 |
|---|---|---|---|---|
| 소스 | 공시 바이트 변경 | 저장된 SHA-256 불일치 | 소스에 결속된 골든 데이터와 청크 검증 실패 | 정당한 소스 교체에도 의도적인 재수집과 검토가 필요 |
| 수집 | 섹션 또는 표가 원시 좌표를 잃음 | 구간 왕복 검증과 코퍼스 테스트 실패 | 잘못된 배치를 영속화하지 않음 | 정규화된 표 텍스트는 여전히 원본 렌더링이 아니라 HTML의 투영 |
| 백필 | 공급자 I/O 도중 행 변경 | 업데이트 전에 저장된 `index_text` 비교 | 오래된 행을 건너뛰고 보고 | 건너뛴 행에는 이후 백필 패스가 필요 |
| 검색 | 쿼리가 비었거나 한도가 잘못됨 | 엄격한 서비스/CLI 검증 | 타입이 지정된 입력 오류, 데이터베이스/공급자 작업 없음 | 호출자가 요청을 수정해야 함 |
| 검색 | 어휘 쿼리가 후보를 반환하지 않음 | 구성 요소 순위와 평가 산출물 | 벡터 후보는 계속 RRF를 통과 | 완화 전 기준선에서 측정되어 M2.4에서 수정됨. 불용어만 있는 쿼리에서는 이 모드가 여전히 존재 |
| 워크플로 | 검색 결과가 비어 있음 | 빈 검색 결과 튜플 | `NOT_IN_DOCS` 반환, 모델을 호출하지 않음 | 코퍼스를 검사하지 않고는 코퍼스 범위 누락과 실제로 존재하지 않는 사실을 구분할 수 없음 |
| 워크플로 | 컨텍스트 예산이 너무 작음 | 전체 청크 단위 계산 | 청크 전체를 제외하고 해당 ID를 기록, 남은 청크가 없으면 거부 | 부분적으로 유용할 수 있는 증거도 제외 |
| 워크플로 | 모델이 알 수 없는 청크를 인용 | 인용 허용 목록과의 교집합 | ID를 제거하고 근거 없는 출력으로 강등 | 구문상 스키마가 유효한 것만으로는 근거성을 증명할 수 없음 |
| 공급자 | 구조화 출력이 두 번 잘못됨 | 엄격한 검증과 한 번의 복구 | 추적 메타데이터와 함께 `schema_rejected` 반환 | 최선 추정 답변을 내보내지 않음 |
| 예산 | 누적 토큰 또는 비용이 한도에 도달 | 노드 실행 전 가드가 이전 추적을 읽음 | `budget_exceeded`를 반환하고 완료된 추적은 유지 | 거의 완료된 실행도 보고서 생성 전에 중단될 수 있음 |
| 서빙 | PostgreSQL 또는 공급자를 사용할 수 없음 | 타입이 지정된 의존성 예외 매핑 | 정보를 노출하지 않는 `503` 리소스 반환 | 가용성 문제는 드러나지만 복구는 여전히 운영 작업 |
| 데모 | 런타임 서비스 실패 | 타입이 지정된 `ApiProblemError` 매핑 | 지원되지 않는 상태와 시도한 호출이 없다는 증거를 렌더링 | 예상하지 못한 예외 클래스에는 여전히 통합 수정이 필요 |

## 평가가 증명하지 못한 것

기록된 실행은 모든 인덱싱 및 쿼리 시간 예산을 통과했지만 프로덕션 검색 품질을 입증하지 못했다.

- 그 실행에서 Recall@5 최고값은 `0.125`였다. 후속 열 실험군 실행은 BM25 어휘 실험군에서 `0.520833`으로 정점을 찍었다.
- 그 실행의 두 청킹 실험군에서는 질문 28개 모두에서 어휘 검색이 후보를 반환하지 않았다.
- 하이브리드 품질은 벡터 품질과 정확히 같았고 지연 시간은 늘었다. 후속 실행에서는 하이브리드가 오히려 순수 어휘 검색에 뒤진다.
- 결정론적 공급자는 안정적인 토큰 해시 기준선이지 의미론적 임베딩 모델이 아니다.
- 골든 사례(28) 전체가 에이전트 선별 상태이며 작성자 승인을 기다리고 있다.

어휘 검색 실패의 메커니즘은 완전한 자연어 질문에서 보존된 용어를 논리곱으로 매칭한 것이었다. 보존된 모든 어휘소를 포함하는 단일 청크가 없었다. 이 진단은 M2.4에서 확인되고 수정되었다. 파싱된 논리곱을 논리합으로 완화하고 `ts_rank_cd`를 extent 거리와 길이로 정규화하며, 다시 측정한 행렬은 [평가 보고서](eval-report.md)에 기록되어 있다.

결정: 이 실행을 재현 가능한 파이프라인 증거로 유지한다. 골든 검토와 별도로 승인된 의미론적 공급자 실험이 완료될 때까지 500자 또는 1200자 실험군이나 벡터와 하이브리드 검색 중 하나를 선택하지 않는다.

## 포트폴리오 고유의 실패 위험

### 합성 데모 증거를 코퍼스 증거로 제시

기본 `CannedDemoService`는 결정론적 UI 픽스처로 만든 Acme 공시, 인용, 문자 구간, 해시를 반환한다. Acme는 커밋된 매니페스트의 티커 4개에 포함되지 않는다. 데모는 지원/미지원 렌더링과 무비용 추적 표시를 증명하지만, SEC 코퍼스에 대한 검색을 증명하지는 않는다.

런타임 어댑터는 M5 도메인 반환 타입을 기준으로 검증되지만 기본 실행기는 여전히 `CannedDemoService`를 선택한다. 기본 UI를 캡처할 때마다 **canned fixture**라고 명확히 표시해야 한다. 명시적으로 주입한 런타임 경로에만 로컬 런타임 레이블을 사용할 수 있다.

### 데모 결합부에서 프로덕션 검색 형태를 강제

`RuntimeDemoService`는 프로덕션 M5 런타임에 맞춰 `RetrievalResult.hits`를 순회한다. 통합 회귀 테스트는 실제 `RetrievalResult`를 생성하고 `results` 속성이 없음을 명시적으로 확인하므로, 과거의 가짜 형태로는 더 이상 잘못된 결합을 통과시킬 수 없다. 이는 주입된 로컬 런타임 투영을 증명할 뿐, 기본 미리 준비된 실행을 코퍼스 기반 실행으로 바꾸지는 않는다.

### UI는 통과하지만 증거 연결부는 실패하는 경우

인용 식별 정보가 없어도 Gradio는 매끄러운 답변을 렌더링할 수 있다. 따라서 집중 데모 테스트는 인용, 구간, 해시 안전 렌더링, 지원/미지원 상태 대비, 주입된 런타임 위임, 타입이 지정된 서비스 실패를 검증한다. 표현 전용 대체 경로가 이 검증을 우회하면 통합 게이트를 중단해야 한다.

### 오래된 스크린샷과 테스트 합계

스크린샷과 통과 수는 코드와 별개로 낡는다. 현재 어떤 스크린샷도 증거로 사용하지 않는다. 통합 이후 스위트는 `697 passed, 1 skipped`를 측정했다. 이는 이전 `691 passed, 1 skipped`를 바탕으로 계산한 값이 아니라 전체를 다시 실행한 결과다.

## 레거시 증거 처리

M6 빌드 계획은 추적 중인 `old/` 파일을 M5까지 마이그레이션 증거로 취급했고, 유용한 교훈을 반영한 뒤에만 제거하도록 했다. 이 조정을 마친 뒤 추적 중인 레거시 파일(22)을 제거했다. 추적하지 않는 `old/.env`는 처음에 사용자 데이터로 보존했지만 승인된 저장소 정리 과정에서 제거했다. 현재 `old/`는 없으며 `scripts/`는 계속 보존한다.

| 레거시에서 얻은 교훈 | 현재 표현 |
|---|---|
| 합성 평가가 완벽한 적중률을 보고할 수 있음 | 전체 M3 매트릭스가 낮고 일관되지 않은 지표를 보고하며 프로덕션 선택을 거부 |
| 빈 검색 결과와 프롬프트 주입에는 보호 동작이 필요 | 타입이 지정된 워크플로 거부, 인용 허용 목록, 회귀 테스트가 안전하게 실패 |
| 근거 없는 증거가 매끄러운 답변이 되어서는 안 됨 | CLI, API, 데모가 `NOT_IN_DOCS` 또는 미지원 상태를 노출 |
| 알 수 없는 모델 가격을 암묵적으로 영으로 처리해서는 안 됨 | 알려진 가격과 명시적 예산을 제공할 때까지 비용 추정이 안전하게 실패 |
| 서비스, API, 데이터베이스, Compose 동작에는 통합 증명이 필요 | 현재 M5/M6 테스트와 Compose 검증이 해당 계약을 담당 |

부분적으로 근거가 있는 결과를 모순으로 바꿨던 과거 출력은 실패 교훈으로만 보존하며 현재 제품의 주장으로 승격하지 않는다. 현재의 타입 지정 경계가 검사할 수 있는 거부를 우선하므로 레거시 대체 데이터는 이식하지 않았다.

## 비용과 비밀의 경계

일반 명령은 결정론적 임베딩을 사용하며 LLM 공급자는 사용하지 않는다. 실제 워크플로 테스트에는 명시적 동의 변수가 필요하고, 런타임에는 주입된 LLM 공급자와 해당 예산이 필요하다. 비밀은 UI 상태, 증거 카드, 추적 또는 영속화한 보고서에 들어가서는 안 된다.

알 수 없는 가격 모델은 영의 추정치를 반환하지 않고 안전하게 실패한다. 유료 실험 전에 최신 공급자 가격을 다시 확인하고, 상한을 승인하고, 모델 접근 권한을 확인하고, 공급자와 비용 출처를 밝힌 별도 산출물을 작성해야 한다.

## 실패 분류 순서

1. 원시 소스 해시와 구간 식별 정보를 검증한다. 2. 벡터와 어휘 구성 요소 순위를 각각 검사한다. 3. 타입이 지정된 워크플로 상태, 성능 저하 이유, 노드 경로를 검사한다. 4. 자격 증명을 노출하지 않고 요청/토큰/비용 추적을 검사한다. 5. CLI, HTTP, 데모의 증거 투영을 비교한다. 6. 데모 어댑터가 프로덕션 `RetrievalResult.hits` 형태를 사용하는지 검증한다. 7. 그 이후에만 표현 또는 배포 동작을 조사한다.

전체 측정 매트릭스는 [eval-report.md](eval-report.md)에 있다. 재현 절차와 중단 조건은 [M6 검증](m6-demo/05-verify.md)에 있다.
