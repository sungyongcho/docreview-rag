# M1.3 실측

설계를 먼저 고정하지 않고 20개 10-K의 Block, 소스 좌표, 표 마크다운을 전수 검사했다. 기계 판정 기준선은 `tests/chunk/golden.py`가 소유하고 이 문서는 설계 이유를 설명한다.

## F1. Block 구간을 원문 좌표로 완전하게 내릴 수 있다

파서가 산출한 본문 Block 51,879개에서 다음 결과를 확인했다.

- `source_pos` 누락: 0
- `end_pos` 누락: 0
- 역방향 구간: 0
- 동일 시작점: 0

BeautifulSoup 출력에서 문자열을 다시 찾지 않고, 원본 줄 오프셋과 다음 Block 시작점을 사용한다. 좌표는 UTF-8 소스 바이트를 줄바꿈 변환 없이 디코딩한 Python 유니코드 코드 포인트 인덱스를 뜻한다. `source_sha256`가 그 좌표가 속한 정확한 스냅샷을 고정한다.

## F2. 텍스트에는 고정 길이 절단보다 Block 묶음이 적합하다

텍스트 Block 길이는 p50 57자, p90 705자, p95 1,000자, p99 1,645자, 최대 3,773자였다.

- 문단 내부는 자르지 않는다.
- 여러 문단을 설정 가능한 목표 크기까지 묶는다.
- 한 문단이 목표보다 길어도 온전히 한 청크로 둔다.

목표 길이는 파괴적 한도가 아니라 묶음 구성을 위한 선호값이다.

## F3. xref Item은 여러 비연속 소스 범위를 가질 수 있다

Intel 문서에서는 하나의 SEC Item이 떨어진 여러 서술 범위를 소유한다. 단순히 같은 `Section.blocks`라는 이유로 묶으면 사이에 생략된 다른 Item까지 인용 구간이 덮는다. 첫 구현에서 이런 중첩 12건이 검출됐다.

`source_group`으로 연속 구간을 분리하고 `source_heading`으로 각 구간의 제목을 보존하자 중첩은 0건이 됐고 이전 구간 제목이 다음 구간의 문맥에 새는 문제도 사라졌다.

## F4. 행 수준 출처 추적 없이 표를 분할하면 인용이 거짓이다

M1.2 마크다운 길이는 p50 401자, p90 1,407자, p95 2,221자, p99 3,651자, 최대 4,129자다. 이전 4,000자 임계치를 넘는 표는 3개뿐이지만 각 분할 조각에 전체 표 HTML 구간을 붙이면 실제 조각보다 훨씬 큰 47K–137K 문자 범위를 인용하게 된다.

따라서 M1.3에서는 **원본 표 하나를 정확히 하나의 청크**로 둔다. 행 분할은 각 행의 소스 좌표를 추적하는 구현이 생긴 뒤에만 허용한다.

## F5. 최종 코퍼스 기준선

| 종류 | 개수 |
|---|---:|
| 텍스트 | 8,083 |
| 표 | 1,089 |
| 합계 | 9,172 |

이 숫자는 검색 품질의 승자가 아니라 의도하지 않은 청킹 변화를 잡는 회귀 기준선이다.

## F6. 합성 문맥은 소스 본문과 분리해야 한다

Item명과 서술 제목 반복은 검색에는 유리하지만 인용된 소스 조각에 그대로 존재하지 않을 수 있다.

- `body`: 소스에서 파생된 증거
- `context_header`: 검색을 위해 반복하는 합성 문맥
- `content`: `context_header + body`, 즉 인덱싱 입력

왕복 검증은 `body`만 판정하고 검색은 `content`를 사용한다.

## F7. Section 순서와 소스 순서는 항상 같지 않다

xref 파서는 SEC Item 순서로 Section을 반환할 수 있다. 최종 청크를 `(start_char, end_char)`로 안정 정렬하고 ordinal을 다시 부여해야 인용과 출력 순서가 원문 순서로 일치한다.

## F8. 기본 텍스트 목표는 어블레이션 실험군이다

`DEFAULT_TARGET_TEXT_CHARS` 1,200자는 시작점이다. M3에서 같은 소스 구간을 기준으로 여러 설정을 평가한다. 청크 ID가 아니라 소스 좌표를 인용으로 사용하므로 설정을 바꿔도 골든 인용을 다시 만들 필요가 없다.
