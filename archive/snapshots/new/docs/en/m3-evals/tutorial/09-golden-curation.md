# M3.5 Tutorial 9 — Golden curation and the taxonomy breakdown

The instrument now measures: tutorial 8 left any configuration runnable against an isolated corpus, with a comparable artifact at the end. What the module still leaves open is growth. Twenty-eight cases are enough to prove the harness works; they are far too few to map where retrieval fails, and nothing so far defines how a new case may enter the suite. Growing the golden set must not **melt the frozen answer key.**

If this layer is absent, growth itself becomes the corruption vector: whoever appends a case also silently redefines what every future run is measured against. The invariant this tutorial builds: **no case enters the measured pool without a recorded human decision, and no promotion ever grants verification.**

**Prerequisite:** The complete M3.4 evaluation path through tutorial 8 passes.

### A generated case is a claim, not evidence

The 28 committed cases were agent-curated: an LLM drafted each question and located its raw-source span, and every case still carries `pending-author-approval` because no human has certified it. That is also how the suite will grow — drafting questions and hunting offsets is exactly the labor worth delegating to a machine. So what happens if a freshly generated case is appended straight into `retrieval.json`?

**The answer key rots silently.** A span whose hash never bound to the corpus scores as an unfindable answer, a near-duplicate of an existing question double-weights one fact in every macro average, and a 46,000-character reconnaissance span games whatever overlap rule is in force. Nothing fails loudly; the metrics just start measuring the generator's habits instead of the retriever.

So generated cases enter through a separate candidate namespace, and `app/evals/curation.py` runs every mechanical gate before a human spends a minute of judgment. The machine proves the case is **well-formed and honestly bound to the source**; only an explicit recorded decision admits it, and silence admits nothing.

```
generated candidates (m3s-*) → machine gates: schema / dedup / source binding → review queue markdown
    → explicit human decisions → promotion mints the next m3c ids → golden-shaped JSON for a reviewed merge
```

The committed file `data/golden/candidates/r1.json` is this checkpoint's live material: four candidates generated by `claude-fable-5` against the immutable corpus — three positives whose answer spans are 104, 176, and 559 raw characters wide, comfortably under the span cap, and one absent case, `m3s-04`, with zero spans by contract. The questions are deliberately worded away from the source vocabulary — "overall sales" where the filing says net revenue, "ten biggest buyers" for top ten customers — so the batch doubles as a paraphrase probe against the suite's known wording bias. The batch passes every machine gate and carries no decisions: each candidate sits at the start of its lifecycle, machine-validated and pending, and the review is yours to run.

This is the same lifecycle the original 28 cases still occupy. Their review queue is committed as `data/golden/REVIEW.md`, where every row reads agent-curated and pending — machine validation completed, author approval outstanding. What moves a candidate forward is the role this tutorial has you build and then perform yourself: the reviewer who writes explicit decisions, renders the queue, and promotes the approved remainder into a **new** golden-shaped file. Merging that file into `retrieval.json` stays a separate, versioned release event, because the committed suite's counts — 28 cases, the category and facet histograms — are frozen as contracts in `tests/evals/golden.py`. Growth must arrive as a reviewed diff that updates the contract in the same commit, never as the side effect of running a script.

```python
class CurationError(ValueError):
    """A candidate file, review decision, or promotion violates the curation contract."""


class CandidateCase(GoldenCase):
    """One generated golden candidate that has not earned an ``m3c`` id yet.

    A candidate carries the full golden payload plus generator provenance, so every
    golden invariant is inherited and enforced at intake. Only promotion may mint a
    golden id, and a candidate can never claim any status beyond the pinned pending
    literals it inherits.
    """

    id: Annotated[StrictStr, Field(pattern=r"^m3s-[0-9]{2}$")]
    generator: Annotated[StrictStr, Field(min_length=1)]

    @field_validator("generator", mode="after")
    @classmethod
    def reject_blank_generator(cls, value: str) -> str:
        """Keep generator provenance non-empty, single-line, and table-safe."""
        if not value.strip():
            raise ValueError("generator must not be blank")
        if "|" in value or "\n" in value:
            raise ValueError("generator must not contain pipes or newlines")
        return value


class ReviewDecision(BaseModel):
    """One explicit human verdict on one candidate. Absence of a verdict is pending."""

    model_config = ConfigDict(extra="forbid", frozen=True)

    candidate_id: Annotated[StrictStr, Field(pattern=r"^m3s-[0-9]{2}$")]
    decision: DecisionLabel
    reviewer: Annotated[StrictStr, Field(min_length=1)]
    note: Annotated[StrictStr, Field(min_length=1)]

    @field_validator("reviewer", "note", mode="after")
    @classmethod
    def reject_blank_text(cls, value: str) -> str:
        """Reject strings that contain only whitespace."""
        if not value.strip():
            raise ValueError("text fields must not be blank")
        return value
```

**What to look for in the code**

- `CandidateCase` subclasses `GoldenCase`, so the absent/positive exclusivity rules, blank-text rejection, span uniqueness, and half-open interval checks from M3.1 all run at intake without being restated.
- Only two things change: the id pattern moves to the `m3s` namespace, and `generator` records which model or person authored the case.
- The pinned literals are inherited too — a candidate cannot even express `human_verified=true` or an approved status. The schema, not discipline, blocks a generated case from claiming certification.
- `ReviewDecision` requires a `reviewer` and a `note`. A verdict nobody signed or explained cannot be audited later, so the model refuses to represent one.

> **Concept — Subclassing as contract narrowing**
>
> A boundary type that must be at least as strict as an existing one should inherit it, not imitate it. Inheritance makes every base validator run on the new type automatically, so the stricter contract is expressed as the base contract plus overrides — nothing is restated, and nothing can be forgotten.
>
> The alternative, copying the validators into a sibling model, creates two contracts that drift independently: the first field added to one and not the other silently loosens a boundary, and no test fails, because each model is still internally consistent. Narrowing by inheritance removes that failure mode structurally — the candidate contract cannot be weaker than the golden contract; it can only add constraints on top.

The other obvious design is no separate namespace at all: hand out provisional `m3c` ids and mark candidates with a flag. That makes the difference between measured truth and unadmitted claim a matter of remembering to check the flag — one forgotten filter and a generated case is indistinguishable from the answer key, and a provisional id minted today can collide with a committed id minted tomorrow. A distinct `m3s` pattern makes the separation mechanical: no code path can confuse the two populations, because no id belongs to both.


Two module-level adapters close the contract layer: list validation for whole candidate and decision files, mirroring the loader's `GOLDEN_CASES`.

```python
def _reject_duplicate_keys(pairs: list[tuple[str, Any]]) -> dict[str, Any]:
    result: dict[str, Any] = {}
    for key, value in pairs:
        if key in result:
            raise CurationError(f"duplicate JSON key: {key}")
        result[key] = value
    return result


def _read_json(path: Path) -> object:
    try:
        return json.loads(
            path.read_text(encoding="utf-8"),
            object_pairs_hook=_reject_duplicate_keys,
        )
    except CurationError:
        raise
    except (OSError, UnicodeDecodeError, json.JSONDecodeError) as exc:
        raise CurationError(f"cannot read valid UTF-8 JSON from {path}: {exc}") from exc


def _candidate_files(path: Path) -> list[Path]:
    if path.is_dir():
        files = sorted(path.glob("*.json"))
        if not files:
            raise CurationError(f"no candidate JSON files found in {path}")
        return files
    return [path]


def _normalized_question(question: str) -> str:
    return " ".join(question.casefold().split())


def _span_identities(case: GoldenCase) -> list[tuple[str, str, int, int]]:
    return [
        (answer.doc_id, answer.source_sha256, answer.start_char, answer.end_char)
        for answer in case.answers
    ]
```

`_read_json` is where the duplicate-key concept box below becomes code, `_candidate_files` keeps directory loading deterministic through `sorted`, and the two extractors define what "the same question" and "the same span" mean everywhere else in the file.

```python
def _validate_unique_candidates(candidates: Sequence[CandidateCase]) -> None:
    ids: set[str] = set()
    questions: set[str] = set()
    identities: set[tuple[str, str, int, int]] = set()
    for candidate in candidates:
        if candidate.id in ids:
            raise CurationError(f"duplicate candidate id: {candidate.id}")
        ids.add(candidate.id)

        normalized = _normalized_question(candidate.question)
        if normalized in questions:
            raise CurationError(f"duplicate normalized candidate question: {candidate.question}")
        questions.add(normalized)

        for identity in _span_identities(candidate):
            if identity in identities:
                raise CurationError(f"duplicate answer span identity in {candidate.id}")
            identities.add(identity)

        for answer in candidate.answers:
            width = answer.end_char - answer.start_char
            if width > MAX_CANDIDATE_SPAN_CHARS:
                raise CurationError(
                    f"{candidate.id} span is reconnaissance, not an answer: "
                    f"{width} > {MAX_CANDIDATE_SPAN_CHARS} chars"
                )


def _validate_disjoint_from_golden(
    candidates: Sequence[CandidateCase],
    golden_cases: Sequence[GoldenCase],
) -> None:
    golden_questions = {_normalized_question(case.question) for case in golden_cases}
    golden_identities = {identity for case in golden_cases for identity in _span_identities(case)}
    for candidate in candidates:
        if _normalized_question(candidate.question) in golden_questions:
            raise CurationError(
                f"{candidate.id} duplicates a golden question: {candidate.question}"
            )
        for identity in _span_identities(candidate):
            if identity in golden_identities:
                raise CurationError(f"{candidate.id} reuses a golden answer span identity")
```

Intake ties both checks to the same strict reading and source binding the golden loader uses.

```python
def load_candidate_cases(
    path: str | Path,
    *,
    golden_cases: Sequence[GoldenCase],
    manifest_path: str | Path = DEFAULT_MANIFEST_PATH,
) -> list[CandidateCase]:
    """Load one file or a directory of candidate files and run every machine gate.

    Structural validation, uniqueness, disjointness from the committed golden set,
    and raw-source binding all run here, so a candidate that survives intake fails
    later only on human judgment, never on mechanics.
    """
    candidates: list[CandidateCase] = []
    for candidate_path in _candidate_files(Path(path)):
        payload = _read_json(candidate_path)
        if not isinstance(payload, list):
            raise CurationError(f"candidate file root must be a JSON array: {candidate_path}")
        try:
            candidates.extend(CANDIDATE_CASES.validate_python(payload))
        except ValidationError as exc:
            raise CurationError(f"invalid candidate cases in {candidate_path}: {exc}") from exc

    _validate_unique_candidates(candidates)
    _validate_disjoint_from_golden(candidates, golden_cases)
    try:
        validate_golden_sources(candidates, manifest_path)
    except GoldenDataError as exc:
        raise CurationError(str(exc)) from exc
    return candidates
```

**What to look for in the code**

- Deduplication runs twice: inside the batch and against the committed golden set. A paraphrased near-duplicate that survives would double-weight one fact in every macro average while looking like growth.
- The 2,500-character span cap is enforced at intake. The committed suite already honors that bound, and a wider span means the generator cited a region instead of locating an answer.
- `validate_golden_sources` is the **same function the golden loader trusts** — hash binding, bounds, and visible-evidence checks are not reimplemented, so the two paths cannot drift apart.
- Every failure surfaces as `CurationError`, including wrapped `GoldenDataError`s. Intake has one error surface, so a caller never has to guess which layer rejected a batch.

Count what intake can reject before a human reads a word: unreadable or duplicate-key JSON, a non-array root, any schema violation the golden contract inherits, duplicate ids, duplicate normalized questions, duplicate span identities, a span wider than the cap, a collision with a committed question, a reused committed span identity, and every source-binding failure. What remains for the reviewer is exactly the residue machines cannot judge — whether the question is unambiguous, whether the cited span really answers it, and whether the category and facet are useful. The committed candidates show the intended scale of an honest answer span: their three positive spans run 104 to 559 raw characters — sentence- and paragraph-sized evidence, well under the 2,500-character cap.

```python
def load_review_decisions(path: str | Path) -> list[ReviewDecision]:
    """Load explicit review decisions. A missing file is an error, never an empty set."""
    decisions_path = Path(path)
    if not decisions_path.is_file():
        raise CurationError(f"decisions file does not exist: {decisions_path}")
    payload = _read_json(decisions_path)
    if not isinstance(payload, list):
        raise CurationError(f"decisions file root must be a JSON array: {decisions_path}")
    try:
        decisions = REVIEW_DECISIONS.validate_python(payload)
    except ValidationError as exc:
        raise CurationError(f"invalid review decisions in {decisions_path}: {exc}") from exc

    seen: set[str] = set()
    for decision in decisions:
        if decision.candidate_id in seen:
            raise CurationError(f"duplicate review decision for {decision.candidate_id}")
        seen.add(decision.candidate_id)
    return decisions


def candidate_states(
    candidates: Sequence[CandidateCase],
    decisions: Sequence[ReviewDecision] = (),
) -> dict[str, CandidateState]:
    """Map every candidate id to pending, approved, or rejected.

    Every decision must name a known candidate, and at most one decision may exist
    per candidate. A candidate without a decision stays pending — silence never
    approves anything.
    """
    known = {candidate.id for candidate in candidates}
    if len(known) != len(candidates):
        raise CurationError("candidate ids must be unique")

    states: dict[str, CandidateState] = {candidate.id: "pending" for candidate in candidates}
    decided: set[str] = set()
    for decision in decisions:
        if decision.candidate_id not in known:
            raise CurationError(f"decision references unknown candidate: {decision.candidate_id}")
        if decision.candidate_id in decided:
            raise CurationError(f"duplicate review decision for {decision.candidate_id}")
        decided.add(decision.candidate_id)
        states[decision.candidate_id] = "approved" if decision.decision == "approve" else "rejected"
    return states


def review_queue_markdown(
    candidates: Sequence[CandidateCase],
    decisions: Sequence[ReviewDecision] = (),
) -> str:
    """Render the deterministic review queue an author walks before any promotion."""
    states = candidate_states(candidates, decisions)
    lines = [
        "| ID | Category | Facet | Positive source | Generator | Decision |",
        "|---|---|---|---|---|---|",
    ]
    for candidate in sorted(candidates, key=lambda case: case.id):
        doc_ids = sorted({answer.doc_id for answer in candidate.answers})
        source = ", ".join(doc_ids) if doc_ids else "none"
        lines.append(
            f"| {candidate.id} | {candidate.category} | {candidate.facet} | "
            f"{source} | {candidate.generator} | {states[candidate.id]} |"
        )
    return "\n".join(lines)
```

**What to look for in the code**

- A candidate with no decision is `pending`, and pending never promotes. The default state of the pipeline is "do nothing."
- A missing decisions file raises instead of reading as an empty set. Absence-as-empty would make a mistyped path indistinguishable from "the author reviewed nothing," and every candidate would quietly stay pending with no signal that the decisions were never found.
- Decisions naming unknown candidates and second decisions for the same candidate are both rejected. A decision log that cannot be replayed onto its batch is corrupt, not merely untidy.
- The queue renders in sorted id order with one row per candidate, so two renders of the same state are byte-identical and compare cleanly with `diff` — the same property every artifact in M3.4 already has.

> **Concept — Fail-closed defaults**
>
> The default state of a pipeline is what it does when a human does nothing, and this pipeline defaults to "do nothing" three separate times. An undecided candidate stays pending, which closes the path where a half-finished review silently admits the cases nobody got to. A missing decisions file raises instead of reading as an empty set, which closes the path where a mistyped path impersonates a completed review that approved nothing. And promotion preserves the pending-approval provenance, which closes the path where admission impersonates certification.
>
> The three choices share one shape: wherever information is absent, the system refuses to advance rather than guessing the permissive interpretation. Fail-open designs leak exactly here — each individual default looks harmless, and the harm appears only when a default fires by accident and nothing records that it did.

Two more decisions hide in plain sight. Decisions live in their own file instead of being edited into the candidate JSON, because a decision is an event with an accountable reviewer and a stated reason: kept separate, the log replays onto the batch from scratch and any corruption is detected, while in-place edits would overwrite the evidence of what the generator originally produced. And the queue renders as markdown rather than a review UI because the queue is itself review evidence — diffable in a pull request, versionable next to the data it describes, byte-stable across renders. `data/golden/REVIEW.md` is exactly this artifact for the original 28 cases.

```python
def _next_golden_number(golden_cases: Sequence[GoldenCase]) -> int:
    return max((int(case.id.split("-", 1)[1]) for case in golden_cases), default=0) + 1


def promote_approved(
    candidates: Sequence[CandidateCase],
    decisions: Sequence[ReviewDecision],
    golden_cases: Sequence[GoldenCase],
    *,
    manifest_path: str | Path = DEFAULT_MANIFEST_PATH,
) -> tuple[GoldenCase, ...]:
    """Mint golden cases from explicitly approved candidates only.

    Promotion re-runs every machine gate — uniqueness, disjointness from the
    committed set, and raw-source binding for the approved cases — assigns the next
    free ``m3c`` ids in candidate-id order, and keeps the pinned pending-approval
    provenance: entering the golden pool queues a case for the author, it never
    certifies one.
    """
    _validate_unique_candidates(candidates)
    _validate_disjoint_from_golden(candidates, golden_cases)
    states = candidate_states(candidates, decisions)

    approved = [
        candidate
        for candidate in sorted(candidates, key=lambda case: case.id)
        if states[candidate.id] == "approved"
    ]
    try:
        validate_golden_sources(approved, manifest_path)
    except GoldenDataError as exc:
        raise CurationError(str(exc)) from exc
    number = _next_golden_number(golden_cases)
    promoted: list[GoldenCase] = []
    for candidate in approved:
        if number > 99:
            raise CurationError("golden id namespace m3c-NN is exhausted")
        payload = candidate.model_dump(mode="json", exclude={"generator"})
        payload["id"] = f"m3c-{number:02d}"
        try:
            promoted.append(GoldenCase.model_validate(payload))
        except ValidationError as exc:
            raise CurationError(f"promoted case from {candidate.id} is invalid: {exc}") from exc
        number += 1
    return tuple(promoted)


def write_golden_cases(path: str | Path, cases: Sequence[GoldenCase]) -> Path:
    """Write promoted cases as a golden-shaped JSON array for a reviewed merge."""
    target = Path(path)
    if target.suffix != ".json":
        raise CurationError(f"golden output must be a .json file: {target}")
    payload = [case.model_dump(mode="json") for case in cases]
    target.write_text(json.dumps(payload, indent=2, ensure_ascii=False) + "\n", encoding="utf-8")
    return target
```

**What to look for in the code**

- Only `approved` candidates promote, in candidate-id order, and ids continue after the highest committed `m3c` number. Promotion order is a property of the data, never of dict iteration.
- The promoted payload drops `generator` and revalidates through `GoldenCase.model_validate`, and every approved span re-binds to its raw source first. The golden contract from M3.1 is the final gate — promotion cannot emit anything the loader would refuse.
- Provenance stays `pending-author-approval` with `human_verified=false`. The admission review decided the case deserves the pool; the author's span-level certification is a separate, later event, and code that granted it here would be fabricating provenance.
- `write_golden_cases` writes a **new** JSON file. Merging into `retrieval.json` is a deliberate, versioned release decision, because the committed suite's counts are frozen contracts in `tests/evals/golden.py` and a silent merge would break them by design.

> **Concept — Admission versus certification**
>
> The pipeline separates two judgments that are easy to collapse into one "approved" bit. Admission asks whether a candidate deserves a slot in the measured pool: the question is well-posed, nothing duplicates it, the span is honestly bound. Certification asks whether the accountable author has verified every fact of the answer against the source. The first is a screening decision a reviewer makes in minutes; the second is the provenance claim the whole golden contract exists to protect.
>
> Conflating them fabricates provenance in the strict sense: a case would carry a verification status that no verification event ever produced. Keeping the stages separate costs one extra field to read; collapsing them costs the ability to ever trust that field again.

Concretely: run promotion against the committed 28-case suite and the first minted id is `m3c-29` — the numbering continues the committed sequence, while the promoted payload still reads agent-curated, pending, unverified. At no point does the pipeline produce a case whose paperwork claims more than what actually happened to it.

```python
def _validated_pairs(
    cases: Sequence[GoldenCase],
    scores: Sequence[CaseScore],
) -> list[tuple[GoldenCase, CaseScore]]:
    """Pair every score with its positive case and reject partial or stray scoring.

    A breakdown over a subset would silently misrepresent a group, so every positive
    case must carry exactly one score, an absent case must carry none, and every
    score must point at a known case.
    """
    index = _positive_case_index(cases)
    if not scores:
        raise ValueError("scores must not be empty")
    if len({score.k for score in scores}) != 1:
        raise ValueError("all case scores must use the same k")

    pairs: list[tuple[GoldenCase, CaseScore]] = []
    scored_ids: set[str] = set()
    for score in scores:
        case = index.get(score.case_id)
        if case is None:
            raise ValueError(f"score references unknown golden case: {score.case_id}")
        if case.category == "absent":
            raise ValueError(f"absent case cannot carry a retrieval score: {score.case_id}")
        if score.case_id in scored_ids:
            raise ValueError(f"duplicate case score: {score.case_id}")
        scored_ids.add(score.case_id)
        pairs.append((case, score))

    unscored = [
        case.id for case in cases if case.category != "absent" and case.id not in scored_ids
    ]
    if unscored:
        raise ValueError(f"positive cases missing a score: {', '.join(sorted(unscored))}")
    return pairs
```

> **Concept — The strict bijection**
>
> A group average is only trustworthy when group membership is closed. If the breakdown accepted whatever scores it was handed, each group's number would be an average over "whichever cases got scored" — the arithmetic would be flawless and the claim false, because dropping one hard case from a group raises its average without leaving any trace in the rendered table. That is the strongest way to lie with a taxonomy: every visible number checks out, and the lie lives entirely in the invisible membership.
>
> Requiring exactly one score per positive case, zero per absent case, and no strays turns incomplete membership from a silent reweighting into a hard error. The table you can render is then the only table that can exist for that run.

The grouping engine sits between the pairing and the public functions: declaration-order iteration, empty groups skipped, one `score_suite` call per group.

<!-- src: app/evals/breakdown.py::_grouped -->
```python
def _grouped(
    pairs: Sequence[tuple[GoldenCase, CaseScore]],
    groups: Sequence[str],
    key: Callable[[GoldenCase], str],
) -> tuple[GroupScore, ...]:
    results: list[GroupScore] = []
    for group in groups:
        members = [score for case, score in pairs if key(case) == group]
        if not members:
            continue
        suite = score_suite(members)
        results.append(
            GroupScore(
                group=group,
                k=suite.k,
                case_count=suite.case_count,
                recall_at_k=suite.recall_at_k,
                hit_rate_at_k=suite.hit_rate_at_k,
                mrr=suite.mrr,
            )
        )
    return tuple(results)
```

```python
def breakdown_by_category(
    cases: Sequence[GoldenCase],
    scores: Sequence[CaseScore],
) -> tuple[GroupScore, ...]:
    """Group suite metrics by golden category in declaration order."""
    pairs = _validated_pairs(cases, scores)
    return _grouped(pairs, get_args(GoldenCategory), lambda case: case.category)


def breakdown_by_facet(
    cases: Sequence[GoldenCase],
    scores: Sequence[CaseScore],
) -> tuple[GroupScore, ...]:
    """Group suite metrics by golden facet in declaration order."""
    pairs = _validated_pairs(cases, scores)
    return _grouped(pairs, get_args(GoldenFacet), lambda case: case.facet)


def breakdown_markdown(dimension: str, groups: Sequence[GroupScore]) -> str:
    """Render one taxonomy breakdown as a compact comparison table."""
    if not dimension.strip():
        raise ValueError("dimension must not be blank")
    if not groups:
        raise ValueError("groups must not be empty")
    lines = [
        f"| {dimension} | Cases | Recall@k | Hit rate@k | MRR |",
        "|---|---:|---:|---:|---:|",
    ]
    for group in groups:
        lines.append(
            f"| {group.group} | {group.case_count} | {group.recall_at_k:.6f} | "
            f"{group.hit_rate_at_k:.6f} | {group.mrr:.6f} |"
        )
    return "\n".join(lines)
```

**What to look for in the code**

- The pairing is a strict bijection: every positive case carries exactly one score, absent cases carry none, and stray or duplicate scores are refused. A breakdown that tolerated a subset would report a group average over whichever cases happened to survive.
- Group order comes from the `Literal` declaration via `get_args`, so tables always read `simple_lookup, exact_number, multi_hop` — no alphabetical surprise, and a group with no scored cases disappears instead of averaging nothing.
- Per-group aggregation reuses `score_suite` from M3.2. There is one implementation of macro averaging in this codebase, so a suite table and a group table can never disagree about arithmetic.
- One aggregate recall hides which kind of question fails; grouped by category, the committed run's failures concentrate sharply instead of spreading evenly. The taxonomy exists precisely to turn one number into a failure map — the per-category reading of the committed run lives in [the evaluation report](../../eval-report.md).

This is where the module's numbers stop being one number. The committed strongest arm — 1200-character BM25 lexical retrieval, aggregate Recall@5 of 0.520833 — regroups into `simple_lookup` at 0.730769 recall over its 13 cases, `multi_hop` at 0.500000, and `exact_number` at 0.000000 on every metric; by facet, `numeric` is the only zero. The aggregate hid a category that fails completely. Reproduce the category table from the committed artifact, offline:

### Focused tests and the contracts they protect

| Value the test breaks | Contract being protected |
|---|---|
| A generated case appended straight to `retrieval.json` | Candidates live in the `m3s` namespace and only promotion mints `m3c` ids. |

The committed-candidates test also re-runs every machine gate against `data/golden/candidates/r1.json`, so a corrupted committed candidate fails the build the same way a corrupted golden case would.

### What you should be able to explain now

- **Why do candidates get their own id namespace instead of provisional `m3c` ids?**
  - **Answer:** The `m3c` namespace is the frozen answer key. If unreviewed cases could carry golden-shaped ids, nothing mechanical would separate measured truth from unadmitted claims, and promotion could silently collide with committed ids.
- **Why does intake deduplicate against the committed golden set and not just within the batch?**
  - **Answer:** A near-duplicate question or reused span identity would enter the same fact twice into macro-averaged metrics, inflating apparent suite growth while double-weighting whatever the retriever already handles.
- **Why is a missing decisions file an error when a missing decision is merely pending?**
  - **Answer:** Absence of one decision is a state the reviewer chose to leave; absence of the whole file is indistinguishable from a mistyped path. Treating it as empty would let a lost decision log read as "nothing approved" with no signal that the review ever happened.
- **Why does a promoted case still say `pending-author-approval`?**
  - **Answer:** The admission decision judged that the candidate deserves the pool; span-level certification by the author is a separate recorded event. If promotion granted verification, the pipeline would fabricate exactly the provenance the golden contract exists to protect.
- **What could a taxonomy breakdown report if it accepted partial scorings?**
  - **Answer:** A group average computed only over the cases that happened to receive scores — the missing members would shift the number invisibly, which is the strongest way to lie with a taxonomy while showing correct arithmetic.
