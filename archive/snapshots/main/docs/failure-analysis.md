# Failure Analysis

실제 평가에서 관찰된 실패 1건을 기록한다 — 원인과 개선안, 그리고 **왜 이 실패가 (상대적으로) 안전한가**.

## 사례: PARTIALLY_SUPPORTED → CONTRADICTED 오분류 (CS-014, CS-015)

### 관찰
claim 평가(`claim_support_cases.json`, 16문항) 결과:

| 골든 라벨 | 정확도 |
| --- | --- |
| SUPPORTED | 4/4 |
| CONTRADICTED | 4/4 |
| **NOT_IN_DOCS** | **4/4** (지어내기 0) |
| PARTIALLY_SUPPORTED | **2/4** — 나머지 2개(CS-014, CS-015)가 `CONTRADICTED`로 |

- 전체 accuracy 0.875, hard-negative accuracy 0.833.
- **유일한 오류 유형이 PARTIALLY_SUPPORTED → CONTRADICTED.**

### 원인
`PARTIALLY_SUPPORTED` 케이스는 **한 주장 안에 지지되는 부분과 모순되는 부분이 공존**한다.
예(CS-013 계열): *"신입은 18일 PTO를 받고 그 전부를 다음 해로 이월할 수 있다"* — 앞(18일)은 HR-001 §2.1이 지지하지만, 뒤(전부 이월)는 §2.3의 5일 이월 상한과 모순.

LLM은 이 "부분 모순"을 감지하면 **전체를 `CONTRADICTED`로 collapse**하는 경향이 있다. `PARTIALLY_SUPPORTED`가 4개 라벨 중 경계가 가장 모호하기 때문이다.

### 왜 안전한 실패인가 (중요)
오류 방향이 **`SUPPORTED`가 아니라 `CONTRADICTED`**다.
- 위험한 실패 = "일부 틀린 주장을 SUPPORTED로 승인" → 사용자를 오도.
- 관찰된 실패 = "부분 모순을 전체 모순으로 더 엄격하게 판정" → **모순을 놓치지 않고 지적**하는 보수적 방향.

claim 검증기의 목적(지어내기·오승인 방지)에 비추면, 이 오류는 **훨씬 덜 위험하다.** 특히 NOT_IN_DOCS가 4/4로 완벽해 "없는 걸 지어내는" 최악의 실패는 0건이다.

### 개선안
1. **프롬프트 강화 (저비용):** 시스템 프롬프트에 *"일부는 지지되고 일부는 모순되면 CONTRADICTED가 아니라 PARTIALLY_SUPPORTED"*를 명시 + few-shot 예시 1~2개.
2. **트레이드오프:** 골든이 16문항으로 작아 프롬프트를 이 2개에 맞춰 튜닝하면 **오버핏 위험.** 오류 방향이 안전하므로, 무리한 튜닝보다 **문서화 + 프롬프트 한 줄 보강** 정도가 합리적.
3. **장기:** PARTIALLY 판정을 "지지 근거"와 "모순 근거"를 각각 추출한 뒤 종합하는 2단계로 분리하면 경계가 또렷해질 수 있음(비용 증가).

### 결론
> 실패는 **PARTIALLY_SUPPORTED라는 가장 애매한 라벨 1종에 국한**되고, **방향이 안전**(모순을 지적하는 쪽)하며, **핵심 안전 지표(NOT_IN_DOCS 지어내기 방지)는 완벽**하다. 프롬프트 한 줄 보강으로 개선 여지가 있으나 작은 골든셋 오버핏을 경계해 현 상태를 정직하게 기록한다.
