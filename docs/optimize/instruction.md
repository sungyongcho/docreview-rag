# 최적화 문서 작성 기준 (M1-M9)

이 디렉토리는 M1부터 M9까지의 최적화 작업을 모듈 단위로 기록한다. 각 문서는 무엇을 바꿨는지, 왜 그 방식이 필요한지, 기존 동작을 어떻게 보존했는지, 이미 확보된 측정 근거가 무엇인지 설명하되 시간순 작업 일지처럼 누적하지 않는다.

Python docstring 작성·수정은 성능 최적화와 독립적인 작업이며 [docstring.md](docstring.md)를 단일 기준으로 사용한다.

## 1. 기록 범위

- 모듈별 디렉토리 `mX/`를 만들고 해당 모듈의 모든 기록을 그 안에 둔다.
- 검수 결과에 따라 상세 문서 `mX/mX-Y.md` 또는 모듈 요약 문서 `mX/mX.md` 중 하나를 사용한다.
- 실제 최적화·리팩터링이나 전체 전후 코드 설명이 필요한 변경은 체크포인트 단위의 `mX/mX-Y.md`에 기록한다.
- 최적화·리팩터링이 필요 없거나 타입·docstring 같은 작은 정합성 수정만 있는 체크포인트는 `mX/mX.md`에 한 줄로 기록한다.
- 체크포인트 표기는 `M2.1`, `M2.2`처럼 실제 숫자를 사용하며 알파벳으로 대신하지 않는다.
- 같은 체크포인트를 `mX/mX.md`와 `mX/mX-Y.md`에 중복 기록하지 않는다. 이후 상세 변경이 생기면 요약 항목을 상세 문서로 옮긴다.
- 해당 모듈에서 검토하거나 실제 반영한 최적화만 기록한다.
- 다른 모듈의 이력, 관련 없는 실행 결과, 외부 문서는 이 단계에서 수정하지 않는다.
- 설명 문장은 한국어로 작성하고, 코드·코드 주석·docstring은 영어로 작성한다.

## 2. 상세 문서 구조 (`mX/mX-Y.md`)

상세 문서에는 다음 네 개의 섹션 표기를 아래 순서 그대로 사용한다.

1. `[개요]` 2. `[원본코드]` 3. `[수정코드]` 4. `[최적화내용]`

### `[개요]`

- 대상 소스 경로와 이 문서에서 다루는 함수 목록을 적는다.
- 병목 또는 개선 후보를 반복 탐색, 할당, 변환 같은 구체적인 단위로 설명한다.
- 이미 기록된 입력 개수, 코퍼스 크기, 반복 횟수 등 측정 범위를 명시한다.
- 코드 블록을 읽기 전에 문서 범위를 파악할 수 있을 정도로만 간결하게 작성한다.

### `[원본코드]`

- 최적화 문서를 처음 생성할 때 해당 단계의 `docs/**/03-build.md`에서 대상 정식 경로에 대응하는 **완성 파일 전체 코드 블록**을 `[원본코드]`에 한 번 그대로 복사한다.
- 완성 파일 전체 코드 블록은 `<!-- complete-files:start -->` 구간에서 `<!-- file: 대상/정식/경로.py -->` 바로 뒤에 있는 Python 코드 블록을 뜻한다. 모듈 docstring의 첫 줄부터 마지막 줄까지 하나도 생략하지 않는다.
- 원본은 **현재 작업 브랜치에 존재하는 해당 단계의 `docs/ko/**/03-build.md`**에서 가져온다. 원본을 찾기 위해 `zero`, `new` 또는 다른 브랜치로 `switch`/`checkout`하지 않는다.
- 다른 브랜치의 `.py` 파일을 직접 복사하거나 `git show 브랜치:경로`로 가져온 코드를 `[원본코드]`에 사용하지 않는다. 현재 작업 브랜치의 `03-build.md` 완성 파일 블록만을 원본 기준으로 삼는다.
- 모듈 docstring, import, 상수, 타입, 클래스, 모든 함수와 메서드, CLI 및 `if __name__ == "__main__":` 블록이 있으면 전부 포함한다.
- `<!-- src: 경로.py::함수명 -->` 형태의 설명용 발췌 블록은 함수 구현이 완전하더라도 `[원본코드]`로 사용하지 않는다. 대상 함수나 클래스만 골라 붙이는 것도 금지한다.
- 현재 `.py` 파일에서 원본을 재구성하거나, 일부 구현을 선별하거나, 코드 정리·번역·포맷 변경을 거쳐 복사하지 않는다.
- 최초 기록 이후에는 최적화 전 비교 기준으로 보존하며 다시 정리하거나 최신 코드로 덮어쓰지 않는다.

### `[수정코드]`

- 정식 소스 경로에 실제 반영된 최종 구현만 기록한다.
- 함수 시그니처, 코드 주석, docstring이 실제 `.py` 파일과 일치해야 한다.
- Docstring은 최적화 여부와 관계없이 [docstring.md](docstring.md)를 따른다.
- 거절한 후보나 중간 실험 코드는 포함하지 않는다.

### `[최적화내용]`

- 함수 또는 파이프라인 순서대로 번호를 붙여 정리한다.
- 각 함수 아래에 `변경`, `이유`, `정합성`, `벤치마크` 문맥을 같은 들여쓰기 수준으로 둔다.
- 변경 내역을 다시 열지 않아도 작동 방식을 이해할 수 있을 만큼 설명한다. 기존 항목을 확장할 때는 현재 설명량의 약 `1.5~2배`를 목표로 하되 의미 없는 문장으로 분량을 채우지 않는다.
- 제거한 할당, 캐시한 조회, 유지한 분기 방향, 추가한 경계 조건처럼 구체적인 내용을 쓴다.
- 실제 최적화를 적용하지 않은 함수는 `함수명: 없음`으로 표시하고 유지한 이유를 남긴다.

아래 들여쓰기 구조를 사용한다.

```text
1. `함수명`

   - **변경**
     - 실제 반영한 방식을 설명한다.
   - **이유**
     - 어떤 반복 작업이나 할당을 줄이는지 설명한다.
   - **정합성**
     - 보존한 동작 계약과 기존 비교 결과를 적는다.
   - **벤치마크**
     - 이미 기록된 측정 결과를 1~2문장으로 요약한다.
```

## 3. 모듈 요약 문서 구조 (`mX/mX.md`)

- 제목은 `# Module X`로 작성한다.
- 최적화나 리팩터링이 필요 없는 체크포인트만 `- M2.1: ...` 형식으로 한 줄씩 기록한다.
- 각 줄에는 코드 역할과 현재 구조를 유지하는 이유를 함께 적는다.
- 타입·docstring처럼 실행 동작을 바꾸지 않는 작은 수정은 필요한 경우 한 단계 들여쓴 글머리표 하나로 덧붙인다.
- 독립 측정값이 없으면 성능 향상을 주장하지 않으며, 상세 코드 블록과 네 개의 상세 문서 섹션을 만들지 않는다.

```text
# Module 2

- `M2.1`: 검색 결과 계약을 정의하는 코드이며 측정된 병목과 리팩터링 필요성이 없어 현재 구조를 유지한다.
- `M2.2`: 임베딩 공급자와 영속화 경계를 분리한 코드이며 필요한 검증과 stale 쓰기 방지 때문에 현재 구조를 유지한다.
  - 작은 타입 정합성 수정이 있다면 이 수준에서만 기록한다.
```

## 4. 벤치마크 작성 규칙

- 측정값이 있으면 최소 1문장, 최대 2문장으로만 요약한다.
- 적용된 입력 범위와 반복 횟수, 전후 시간, 증감률을 한 흐름으로 적는다.
- 해당 최적화에 이미 기록된 결과만 재사용한다. 문서 정리 작업에서는 벤치마크를 다시 실행·재생성·추정하거나 새로운 수치를 만들지 않는다.
- 독립 측정값이 없으면 없다고 명시하고 성능 향상을 주장하지 않는다.
- 출력 동일성은 시간 측정이 아니며, 더 빠른 결과 역시 의미 동등성을 증명하지 않는다. 정합성 근거와 성능 근거를 분리해서 적는다.

## 5. 문장과 목록 형식

- 설명은 한국어, 코드 관련 식별자·주석·docstring은 영어를 사용한다.
- 같은 문맥의 글머리표는 동일한 들여쓰기 수준에 배치하고 세부 근거만 한 단계 안쪽에 둔다.
- 함수명, 식별자, 명령, 정확한 수치는 백틱으로 감싼다.
- 글머리표 하나에는 한 가지 핵심만 두고, 제약을 설명할 때만 두 번째 문장을 사용한다.
- 본문 설명을 확장하더라도 벤치마크 항목은 반드시 1~2문장으로 유지한다.
- 실험 과정을 시간순으로 이어 붙이지 않는다. 원본, 최종 코드, 채택한 변경, 짧은 근거만 남긴다.

## 6. 리팩터링 기록 (`refactor.md`)

- 여러 파일·모듈에 걸친 동작 보존 리팩터링은 체크포인트 문서가 아니라 [refactor.md](refactor.md)에 기록한다.
- 패스 단위 섹션(`## R1 — ...`) 아래 테마별 항목을 `[대상]` `[변경]` `[이유]` `[정합성]` 표기로 정리하고, 검토 후 보류한 항목도 사유와 함께 남긴다.
- 리팩터링이 상세 문서의 대상 파일을 바꿨다면 §2의 규칙대로 해당 `[수정코드]`를 실제 소스와 다시 맞춘다. `[원본코드]`와 기존 벤치마크 기록은 그대로 둔다.
- `mX/mX.md` 하단의 `[refactor]` 절에는 해당 모듈에 반영된 항목을 한 줄씩 가리키는 포인터만 담는다.

## 7. 문서 업데이트 순서

1. 대상 모듈과 함수 목록을 먼저 확정한다. 2. 이 기준과 해당 모듈의 기존 최적화 문서를 읽는다. 3. 검수 결과에 따라 상세 `mX/mX-Y.md`와 요약 `mX/mX.md` 중 하나를 선택한다. 4. 요약 문서는 해당 체크포인트의 역할과 유지 이유만 간결하게 적는다. 5. 상세 문서의 `[원본코드]`는 보존하고, 구현 변경이 있을 때만 최종 `[수정코드]`를 갱신한다. 6. `[최적화내용]`의 각 함수를 동일한 문맥/들여쓰기 구조로 정리한다. 7. 문서만 다듬는 작업에서는 기존 정합성 및 벤치마크 기록을 재사용하고 측정을 다시 돌리지 않는다. 8. 구현 코드가 바뀌었다면 [docstring.md](docstring.md) 기준도 함께 적용하고 `[수정코드]`와 정식 소스를 맞춘다. 9. 두 번째 최적화 이력 섹션을 덧붙이지 말고 현재 상태를 설명하는 하나의 문서로 마무리한다.
