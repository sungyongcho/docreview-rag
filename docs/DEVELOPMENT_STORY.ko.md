# DocReview RAG — 개발 기록 {#development-log}

> 공시 문서를 검색해 근거와 함께 답하는 RAG 워크플로를 만들며, 파싱부터 평가·배포 준비까지 전 과정을 직접 구현한 기록입니다.
> 제 역할은 요구사항·기준·판단을 정하는 것이었고, 구현의 상당 부분은 AI와 함께 진행했습니다. 확인한 사실과 아직 확인하지 못한 것을 구분해 적었습니다.

<!-- heading-alias: 한눈에 -->
## 한눈에 {#at-a-glance}

- **무엇**: 채팅 데모가 아니라, 문서 근거·인용·평가·실행 기록을 갖춘 LLM/RAG 리뷰 워크플로입니다.
- **내 역할**: 범위와 수용 기준 정의, 아키텍처·정책 판단, 결과 검증, AI 작업 지시·리뷰.
- **스택**: Python · FastAPI · Pydantic · SQLAlchemy · PostgreSQL/pgvector · Docker Compose · pytest · Next/React 웹 UI · Ollama(로컬 모델).
- **핵심 구현**: HTML/XML 파싱과 표 정규화, 구조 인지 청킹, 하이브리드 검색(RRF), 선택형 cross-encoder 리랭킹, 구조화 출력과 실패 분류, 골든셋 기반 검색 평가, 비용·요청 한도.
- **검증 방식**: 모듈별 회귀 테스트, 실제 PostgreSQL 검증, 실행 기록을 통한 결과 확인.
- **경계**: 라이브 프로덕션 서비스가 아닙니다. 배포 스펙과 절차는 확정했고, 답변 품질의 최종 평가는 사용자 검수 전입니다.

### 따라 만들기에서 구조 이해로 {#learning-by-rebuilding}

강의 코드를 따라 완성하는 것만으로는 각 단계가 왜 필요한지 충분히 설명하기 어려웠습니다. 핵심 흐름을 직접 다시 구성하면서 문서를 어떻게 나눌지, 임베딩은 어디까지 재사용할지, 검색 점수는 무엇을 반영하는지 하나씩 확인했습니다.

<!-- heading-alias: 1-1-파싱-api-수집과-html-파싱 -->
### 1-1. 파싱 — API 수집과 HTML 파싱 {#parsing}

SEC EDGAR와 DART API로 원문을 받아 파싱하는 단계는 일부러 직접 구현했습니다. 두 형식을 직접 읽어본 적이 없어 구성 요소 파악이 필요했고, 그 과정에서 다음 단계인 청킹의 기준(무엇을 한 덩어리로 볼 것인가)이 자연스럽게 보였습니다.

```text
SEC/DART API ──download──▶ manifest          (SHA-256으로 식별되는 원문 artifact)
                              │
                              ▼
                  HTML/XML normalize          (script/style/img 제거, iXBRL unwrap)
                              │
                              ▼
                  leaf blocks                 heading / paragraph / table
                              │               + 원문 문자 오프셋(source_pos)
                              ▼
                  segment by section          SEC: Item 헤딩 · DART: SECTION/TITLE
                              │
                              ▼
                  ParsedFiling ──▶ 청킹 단계
```

**기법**은 **BeautifulSoup + html.parser 기반 DOM 텍스트 추출(태그 스트리핑)** 입니다. `script/style/noscript/img`는 제거하고, 비렌더 iXBRL `ix:header`는 통째로 버리며 나머지 `ix:*`는 unwrap해 숫자를 보존합니다. 원문 라인·오프셋은 `html.parser`의 `sourceline/sourcepos`로 계산해 남깁니다. 이미지·OCR·PDF 파싱은 쓰지 않았습니다. 공시 본문에서 이미지가 차지하는 정보 비중이 낮다고 판단해 텍스트·표 중심으로 갔습니다.

**SEC 세그멘테이션**은 `Item N.` 제목을 폰트 굵기·크기 휴리스틱으로 찾습니다. 문서마다 스타일이 달라, 이슈어별로 "굵기 ≥700·크기 10pt" 같은 프로파일을 학습해 `data/profiles/*.json`에 저장하고 검증 실패 시 다시 학습합니다. 본문에 Item 제목이 아예 없는 문서(Intel 2019+)는 SEC가 요구하는 Cross-Reference Index와 회사 목차를 페이지 범위로 조인하는 fallback을 씁니다.

```text
HTML blocks
   │
   ├─ "Item 1A. Risk Factors"가 학습된 스타일 프로파일을 통과? ── 예 ─▶ Section 경계
   │        (최소 5개 관측, 목차처럼 보이면 기각)
   │
   └─ Item 헤딩이 전혀 없음 (Intel 2019+) ──▶ XRef Index + TOC 페이지 조인
                                               + 2차 스윕으로 누락 Item 회수
```

**DART**는 휴리스틱 없이 마크업을 읽습니다. `SECTION-1`의 `TITLE`이 12개 대분류(I~XII)라 그대로 신뢰하고, 커버리지가 90% 미만이면 경고, 하나도 없으면 실패합니다. 인코딩은 permissive 선언(ISO-8859-1 등)을 신뢰하지 않고 `utf-8/utf-8-sig/cp949/euc-kr` allow-list + strict 디코드를 씁니다.

**표 정규화**는 별도 파이프라인입니다. `rowspan/colspan`을 전개해 밀집 그리드로 만들고, 빈 행·열을 제거하고, 단위(`$`, `%`, `₩`) 열을 값 쪽으로 병합하고, 헤더를 모양으로 추론한 뒤 마크다운으로 직렬화합니다. 헤더를 못 찾으면 빈 헤더로 두고 데이터 행을 헤더로 승격하지 않습니다.

```table-normalize-demo
```

`(1,234)` 같은 음수 표기는 그대로 둡니다. 인용이 독자가 보는 filing과 일치해야 하고, 여기서 정규화하면 되돌릴 수 없기 때문입니다. 원문 셀의 span·소유권도 별도 구조로 보존해, 이후 분할에서도 어느 셀에서 왔는지 추적할 수 있게 했습니다.

> **왜 직접 파싱했는가**: 기성 파서를 붙였다면 빨랐겠지만, Item/표/문단이 어떤 경계로 나뉘는지 모른 채 다음 단계를 설계하게 됩니다. 파싱에서 얻은 구조 이해가 청킹·인용 설계의 기준이 됐습니다.

<!-- heading-alias: 1-2-청킹-구조를-지키는-분할 -->
### 1-2. 청킹 — 구조를 지키는 분할 {#chunking}

청킹은 "검색에 쓰기 좋은 단위"로 문서를 나누는 작업입니다. 기준은 두 가지였습니다. 표·제목·문단 경계를 넘지 않게 나누고, 나눈 조각이 원문 위치를 그대로 가리키게 합니다.

| 파라미터 | 값 | 이유 |
|---|---|---|
| target tokens | 2,048 | 임베딩 입력의 목표 크기 |
| max tokens | 8,192 | 모델 입력 한도(자르지 않고 실패/분할) |
| max chars | 12,000 | 문자 기반 상한 |
| overlap | 없음 | 원문 span 정렬·중복 인용 방지 |
| context header | citation + 제목 + 헤딩 | 떨어져 검색돼도 문맥 유지 |

```chunk-map
```

표는 우선 행 단위로 묶고, 한 행이 너무 크면 셀 단위로, 그것도 안 되면 문장 단위로 내려갑니다. 어느 단계에서도 헤더와 단위 캡션을 반복해 붙이므로 값이 문맥을 잃지 않습니다. 단위 캡션(`(단위: 백만원)`)은 다음 표에만 유효하게 전달하고, 다른 표로 새면 버립니다. 임베딩 provider가 정해지면 그 모델의 실제 tokenizer와 입력 한도로 예산을 다시 계산합니다.

> **왜 overlap이 없는가**: 인용 정확도가 최우선이었습니다. 겹치는 조각은 같은 문장을 두 번 인용할 수 있고, 원문 span 추적을 흐립니다. 대신 문맥은 컨텍스트 헤더로 보완합니다.

### 1-3. 임베딩 — 벡터화와 차원 {#embeddings}

임베딩은 문장을 벡터로 바꿔 의미 기반 검색을 가능하게 합니다. OpenAI `text-embedding-3-large`에 **`dimensions=384`를 지정해** 축소된 벡터를 요청하고(Matryoshka 방식의 차원 축소), 설정과 DB 벡터 폭도 384차원으로 맞췄습니다. provider·모델·차원·tokenizer 조합이 벡터 identity로 저장돼, 벡터 공간이 바뀌면 조용히 섞이지 않고 재임베딩 대상이 됩니다.

```text
문서 청크(index_text) ─┐
                       ├─ 같은 provider·같은 모델·같은 차원 ─▶ 384차원 벡터 ─▶ pgvector
질문(정규화 텍스트)   ─┘        (embed_query = embed_documents([q])[0])
```

**검색이 성립하는 이유.** 질문과 각 청크를 같은 벡터 공간에 독립적으로 인코딩하는 bi-encoder 방식의 구조라서, 검색은 벡터끼리의 비교 — 여기서는 pgvector 코사인 유사도 — 가 됩니다. 독립 인코딩이기에 사전 계산이 가능합니다. 청크 벡터는 한 번 저장해 두고 청크 텍스트와 임베딩 identity·설정이 호환되는 동안 재사용하며, 질의 벡터는 요청 시점에 계산합니다 — 번역된 질의 변형도 각자의 임베딩을 받습니다. 두 인코딩 역할은 하나의 가중치를 공유할 수 있고 모델 인스턴스 두 개를 요구하지 않습니다. 이는 검색 아키텍처에 대한 설명이지 외부 공급자 모델 내부에 대한 주장이 아닙니다.

학습·테스트용으로는 결정적 해시 기반 임베딩(재현 가능)과 로컬 sentence-transformers(MiniLM) 경로를 별도로 두었습니다. Hugging Face 등에서 다양한 모델이 서빙된다는 점도 이 단계에서 알게 됐습니다.

**차원은 문장의 의미를 표현하는 벡터의 크기입니다.** 벡터 하나를 구성하는 숫자의 개수이며, 모델마다 기본 출력 크기가 다릅니다. 로컬 경로의 `all-MiniLM-L6-v2`는 384차원을 출력하고, `text-embedding-3-large`는 기본 3072차원을 출력합니다. 이 프로젝트는 OpenAI 모델의 출력을 384차원으로 축소해 사용합니다. [Sentence Transformers 공식 예제](https://www.sbert.net/docs/quickstart.html), [OpenAI 임베딩 문서](https://developers.openai.com/api/docs/guides/embeddings)

[Matryoshka 학습](https://www.sbert.net/examples/sentence_transformer/training/matryoshka/README.html)은 전체 벡터뿐 아니라 앞부분의 작은 벡터도 유용하도록 함께 학습합니다. 이 특성으로 의미 정보를 담은 표현을 더 작은 크기로 사용할 수 있습니다. 축소를 지원하는 OpenAI API에 원하는 차원을 전달하며, 임의의 모델에서 벡터를 잘라 같은 효과를 기대하지는 않습니다.

3072에서 384로 줄이면 저장하고 비교할 성분 수는 1/8이 됩니다. [pgvector의 저장식](https://github.com/pgvector/pgvector#vector-type) `4 × 차원 + 8`로 계산하면 벡터 값 하나는 12,296바이트에서 1,544바이트로 작아집니다. 전체 저장 용량과 응답 시간에는 인덱스·모델 호출 등 다른 요소도 영향을 줍니다. 또한 [OpenAI API 요금은 입력 토큰 기준](https://developers.openai.com/api/docs/guides/embeddings)이므로 출력 차원 축소와 별개입니다.

**현재 문서 범위에서는 384차원을 유지했습니다.** 문서 규모와 주제의 다양성이 커지거나 더 세밀한 의미 구분이 필요해지면, 검색 품질과 지연 시간을 비교해 차원 확장을 검토할 수 있습니다. 현재는 비교적 소규모의 코퍼스에서 보고서 형식과 섹션 구조가 일정한 공시를 대상으로 하며, 이 범위에서 검색·답변 흐름의 동작을 확인했기에 384차원을 계속 사용하기로 했습니다.

<!-- heading-alias: 1-4-키워드-인덱싱과-하이브리드-검색 -->
### 1-4. 키워드 인덱싱과 하이브리드 검색 {#retrieval}

키워드 검색은 벡터 검색이 놓치는 고유명사·숫자·표현을 잡아줍니다. 기본 어휘 랭커는 PostgreSQL `ts_rank_cd`(커버 밀도)이고, BM25는 별도 옵션 랭커로 구현해 비교했습니다.

**한국어 처리**가 이 단계의 핵심 문제였습니다. `english` 설정은 한국어를 형태소로 분해하지 못하고 교착어 변형이 갈라집니다. 그래서 한국어 텍스트는 `simple` 설정에서 겹치는 문자 bigram으로 색인하고, 질의에도 같은 함수를 적용합니다. DART FY2024 24개 양성 문항에서 실제로 측정한 값(코드 주석 기록)은 다음과 같습니다.

| 한국어 어휘 랭커 | hit_rate@5 | MRR@5 |
|---|---|---|
| BM25 · bigram | 0.875 | 0.684 |
| BM25 · trigram | 0.792 | 0.649 |
| BM25 · whitespace | 0.792 | 0.653 |
| ts_rank_cd (모든 변형) | 0.33–0.42 | — |

**BM25**는 언어별 통계 테이블(`chunk_terms`, `chunk_lengths`, `lexeme_stats`, `bm25_corpus_stats`)을 두고 SQL로 계산합니다.

$$
\begin{aligned}
\mathrm{idf}_{\mathrm{lucene}} &= \ln\!\left(1 + \frac{N - df + 0.5}{df + 0.5}\right)\\
\mathrm{length\_norm} &= 1 - b + b \cdot \frac{dl}{\overline{dl}}\\
\mathrm{saturation} &= \frac{tf \cdot (k_1 + 1)}{tf + k_1 \cdot \mathrm{length\_norm}}\\
\mathrm{score} &= \sum_{t} \mathrm{idf}_t \cdot \mathrm{saturation}_t \qquad (k_1 = 1.2,\; b = 0.75)
\end{aligned}
$$

```bm25-demo
```

가장 인상적이었던 건 수식이 반복을 다루는 방식이었습니다. **IDF는 흔한 단어의 비중을 낮추고, tf 포화는 같은 단어를 반복해서 얻는 이득을 제한합니다.** 공시에 자주 나오는 "회사"·"재무"보다 발행사 이름이나 드문 용어가 문서를 구별하는 데 더 기여하는 셈입니다. 점수는 단순한 등장 횟수보다 질문을 얼마나 구별력 있게 설명하는지를 반영합니다. 위 미니 실험에서 k1·b를 바꾸면 차이를 확인할 수 있습니다.

구현에는 로버트슨 IDF도 포함했습니다. 청크가 바뀌어 통계가 오래되면 검색을 중단하고 재빌드를 안내합니다. 잘못된 통계로 그럴듯한 순위를 내는 것보다, 갱신이 필요하다고 알리는 편을 택했습니다.

**하이브리드 결합**은 순위 기반 점수 결합(RRF)입니다. 각 검색 경로의 순위를 역순위 기여로 환산해 더하며, 벡터·어휘 원점수나 원시 순위 번호를 직접 더하지 않습니다. 아래 미니 실험의 두 레인(벡터·어휘)에서 A와 B의 기여를 계산하면 다음과 같습니다.

$$
\mathrm{RRF}(d) = \sum_{\ell}\, \frac{1}{k + \mathrm{rank}_{\ell}(d)}, \qquad
\mathrm{A} = \tfrac{1}{60+1} + \tfrac{1}{60+3}, \qquad \mathrm{B} = \tfrac{1}{60+2} + \tfrac{1}{60+1}
$$

수식의 k=60은 완충 상수 `rrf_k`로, 최종 반환되는 결과 수 k=5와는 다른 값입니다. 각 문서는 리스트마다 처음 등장한 순위로만 기여합니다.

```rrf-demo
```

```text
질문 ─┬─▶ 벡터 검색 (pgvector 코사인, exact scan) ─┐
      │                                            ├─▶ RRF (순위 기반 점수 결합)
      └─▶ 어휘 검색 (ts_rank_cd / BM25 / bigram) ──┘            │
                                                  융합 후보 풀 (≤ candidate_k)
                                                              │
                                              (선택) cross-encoder
                                              ms-marco-MiniLM-L-6-v2가
                                              각 (질문, 구절) 쌍에 점수
                                                              │
                                                              ▼
                                      최종 top-k ─▶ 답변·인용 검증
```

후보군은 $\mathrm{candidate\_k} = \max(20,\, 4k)$가 기본이고, 정확도 프리셋에서만 cross-encoder 리랭커를 붙입니다. ANN 인덱스는 측정 근거가 생기기 전까지 두지 않았습니다(정확 스캔이 재현성에 유리).

**선택형 리랭커가 하는 일.** 두 검색 경로가 후보를 찾으면 RRF가 순위를 합쳐 크기가 제한된 풀을 만듭니다. 리랭킹은 이렇게 이미 검색된 풀을 재정렬하는 작업이고, 이 프로젝트에서는 cross-encoder가 그 작업을 수행하는 모델입니다 — 리랭킹과 동의어가 아닙니다. cross-encoder는 (질문, 구절) 쌍 하나를 하나의 입력으로 함께 읽어 관련도 점수를 내기 때문에 토큰 상호작용을 직접 모델링할 수 있습니다 — 질문의 키워드가 빽빽하지만 다른 관계를 다루는 구절이, 물은 관계를 실제로 답하는 구절 아래로 갈 수 있습니다(측정 결과가 아닌 개념 예시). 저장된 벡터가 아니라 텍스트 쌍에 점수를 매기므로 리랭커를 켜거나 꺼도 코퍼스 재임베딩은 필요 없고, 풀에 들어오지 못한 근거를 되살리지도 못합니다.

**점수를 매기는 범위.** 리랭커는 융합 풀 전체에 점수를 매깁니다 — 코퍼스의 모든 청크를 돌지도 않고, 반환될 5개만 보지도 않습니다. 기본 프리셋으로 보면 Balanced는 k=5 / candidate_k=20 / 리랭커 없음, Korean은 k=5 / candidate_k=30 / 리랭커 없음, Accuracy는 k=5 / candidate_k=50 / cross-encoder입니다 — Accuracy는 최종 5개를 반환하기 전에 최대 50개의 (질문, 구절) 쌍에 점수를 매길 수 있습니다. 쌍 평가는 백엔드의 로컬 배치 추론이지 50번의 별도 네트워크·API 요청이 아니며, 최초 사용 시 필요한 모델 가중치 적재·가중치 캐시·질의 임베딩 API 호출·쌍 추론은 서로 다른 비용입니다. 후보 수를 늘리거나 cross-encoder를 쓰면 연산량과 지연이 늘 수 있고, 결과 품질은 프리셋 이름이 아니라 도메인·언어·코퍼스 적합도가 좌우합니다. 답변 생성과 인용 검증은 최종 top-k 이후의 뒷단계에서 이뤄집니다.

> **왜 RRF인가**: 벡터 점수와 어휘 점수는 스케일이 달라 직접 더하면 한쪽이 다른 쪽을 압도합니다. 순위만 쓰면 랭커를 추가해도 안정적이고, 대신 점수 크기 정보는 버립니다.

**서버가 규칙으로 확인할 수 있는 일을 모델에게 다시 추측시키지 않는 것**이 출발점입니다. 요청 전체가 규칙에 맞으면 분류 호출을 건너뛰어 지연·비용·편차를 줄입니다. 다만 사람이 보기에 명확한 요청도 규칙에는 맞지 않을 수 있습니다. 알려진 기업 하나만 보고 함께 물은 모르는 기업을 버리지는 않습니다. 규칙은 다음 경우를 구분합니다.

- 요청 대상이 모두 알려진 별칭인 분석 요청은 분석 경로로 보내고,
- 정확히 일치하는 인사·감사·사용법 질문은 고정 서비스 안내를 받으며,
- 역할극처럼 명백히 범위 밖인 요청은 범위 안내를 받고,
- 명확히 이어지는 후속 질문은 제한된 맥락이 가리키는 기존 경로를 유지합니다.

후속 질문은 제한된 수의 이전 사용자 질문이 규칙을 통과했을 때 이어받습니다. 이는 이전 실행이 성공했다는 증거는 아닙니다. 규칙으로 정하지 못한 요청만 모델 분류로 넘기며, 분류 실패는 자유 형식 답변으로 대체하지 않고 기술 오류로 기록합니다.

<!-- details: routing-call-records | 분류 호출과 대화 기록의 정확한 의미 -->

요청당 분류 판단은 한 차례지만, provider 재시도와 스키마 복구는 추가 호출 시도를 만들 수 있습니다. 발생한 시도는 각각 측정합니다. 대화 기록 스키마는 role과 text만 저장하므로 이전 텍스트가 규칙에 맞는 것과, 이전 요청이 실제로 성공한 것은 구분해야 합니다.

1단계의 별칭·기업·연도·문서 확인은 모델의 답을 신뢰하는 대신 서버가 제공하는 코퍼스 목록과 대조합니다. 식별하지 못한 대상을 전체 코퍼스 검색으로 넓히지 않습니다.

<!-- /details -->

첫 번째는 화면의 0단계에 해당하는 **경로 결정**입니다. 요청을 기업·재무·공시 분석, 제한된 서비스 안내, 서비스 범위 밖으로 분류합니다. 회사의 성장·실적을 묻는 질문은 SEC·DART를 직접 언급하지 않아도 분석으로 분류되고, 인사·감사·사용법 질문은 정해진 서비스 안내를 받습니다. "고양이와 대화하기" 같은 일반 대화·역할극은 여기서 서비스 범위 안내로 끝나며 자유 형식의 모델 답변을 생성하지 않습니다. 규칙으로 정리되지 않을 때 분류 판단은 모델 호출로 이뤄집니다 — 그래서 조기 종료가 호출·비용 0을 뜻하지 않고, "분류 호출 없음"이 "모델 호출 없음"을 뜻하지도 않습니다. 진행되는 요청이 질의를 임베딩할지, 답변 모델을 호출할지는 검색 방식과 도달 단계에 따라 달라지며, 실행 기록에는 실제 발생한 호출만 남습니다.

두 번째는 1단계 **질문 의도 확인**입니다. 요청한 기업·기간·선택한 문서 범위를 식별하고, 지원하는 별칭을 제공 코퍼스에 있는 기업으로 해석한 뒤, 서버의 실제 제공 코퍼스와 대조합니다. 모델이 질문에서 기업명을 식별할 수는 있지만 해당 공시가 서버에 있는지는 서버가 실제 목록으로 확인합니다. "샌디스크 성장 요인"은 유효한 분석 의도로 0단계를 통과하지만 현재 코퍼스에 샌디스크가 없어 여기서 멈춥니다.

제공하지 않는 기업은 잘못된 질문도 아니고 그 회사가 없다는 증거도 아닙니다. 이름이 모호하면 확인을 요청하고, 기업을 찾지 못했다고 검색을 전체 기업으로 넓히거나 다른 기업으로 대체하지 않습니다. NVIDIA 같은 별칭은 제공 코퍼스의 NVDA 기업으로 해석될 수 있지만, 수집 대상 기업 목록에 이름이 올라 있다는 사실만으로 공시가 있는 것은 아닙니다. 요청한 연도나 선택한 문서 범위에 해당하는 제공 공시가 없으면 검색 전에 멈춥니다.

<!-- heading-alias: 질문-언어가-코퍼스를-정하지-않는-이유 -->
#### 질문 언어가 코퍼스를 정하지 않는 이유 {#language-and-scope}

영어 질문에는 영어 공시만 검색하면 될 것처럼 보입니다. 하지만 "Compare Nvidia and Samsung revenue"에는 NVIDIA의 SEC 공시와 삼성전자의 한국어 DART 공시가 모두 필요합니다. 질문 언어로 문서를 거르면 검색을 시작하기도 전에 삼성전자 자료가 빠집니다. 이미 범위에서 제외한 근거는 번역이나 다국어 임베딩으로도 되살릴 수 없습니다.

그래서 질문 언어와 문서 범위를 분리했습니다. 자동 범위에 추가 제한이 없는 전체 기업 비교라면, 영어·한국어 어느 쪽으로 물어도 SEC와 DART가 모두 검색 대상입니다. 반면 사용자가 SEC를 선택하면 SEC로 제한합니다. 기업·연도·문서 선택과 명시적 문서 언어 필터도 그대로 적용하며, 질문의 언어만으로 이 제한을 덮어쓰지 않습니다. SEC를 선택한 채 DART 기업을 지명하면 기업을 몰래 빼거나 선택을 무시하는 대신 범위 충돌을 알립니다.

이 분리로 질문 언어 때문에 필요한 출처가 빠지는 문제를 막지만, 언어 간 검색 품질까지 해결되는 것은 아닙니다. 범위에 포함돼도 적절한 구절을 찾지 못하거나 답변 근거가 부족할 수 있습니다. 아래에서 두 설정을 바꿔 보면 차이가 보입니다. 질문 언어는 문장을 바꾸고, 명시한 출처는 검색할 수 있는 문서를 바꿉니다.

#### 질문 언어와 답변 언어 {#answer-language}

**기본은 질문과 같은 언어로 답변하는 것입니다.** 한국어로 NVIDIA를 물으면 영어 SEC 공시를 읽어도 한국어로, 영어로 삼성전자를 물으면 한국어 DART 공시를 읽어도 영어로 답하도록 합니다. 사용자가 다른 답변 언어를 명시했을 때만 예외로 처리합니다.

검색 범위만 분리해도 이 규칙이 자동으로 지켜지지는 않았습니다. 이전에는 답변 프롬프트에 언어 규칙이 없었고, 후속 질문을 검색용으로 재작성하면 원래 질문의 언어도 흐려질 수 있었습니다. 이제 서버가 원래 질문을 `original_query`로 보존하고, 검색용 `query`와 따로 모델에 전달합니다. 기존 근거 평가·답변 호출의 시스템 프롬프트가 원래 질문을 언어 기준으로 삼으므로, 언어 판별을 위한 모델 호출은 추가하지 않습니다.

이 규칙은 답변과 설명에 적용하며, 인용 원문·회사 코드·`SUPPORTED` 같은 판정 값은 바꾸지 않습니다. 근거 부족으로 답변 생성 전에 종료되거나 인용 검증에서 답변이 제외될 때도, 서버의 고정 안내를 원래 질문의 한·영 언어에 맞춰 표시합니다. 이를 위한 모델 호출은 없습니다. 한·영이 섞인 모델 답변은 회사명이나 인용문보다 질문 문장의 언어를 따르도록 지시합니다. 프롬프트 전달과 언어 요청 보존은 회귀 테스트로 확인하지만, 모델 출력의 언어를 별도로 검사하거나 번역을 재시도하는 구조는 아닙니다.

<!-- heading-alias: 판정과-기록 -->
#### 판정과 기록 {#verdicts}

받아들여진 요청과 사용 가능한 범위만이 근거 검색·관련 근거 선택·답변/인용 검증으로 진행합니다. 근거 평가까지 도달한 문서 검토 요청의 판정은 `SUPPORTED`와 `NOT_IN_DOCS` 둘 중 하나입니다. `SUPPORTED`는 "근거가 있어 보인다"가 아니라 "인용이 검증을 통과했다"는 신호이고, 스키마가 인용 없는 지지 답변 자체를 거부합니다. 모델이 요청한 인용이 검증에서 걸러지면 부분 인용 답변을 보내는 대신 `support_downgraded`로 전체 결과를 부재로 내립니다. 근거 부족 판정(`NOT_IN_DOCS`)과 운영 실패(provider·노드·예산)는 서로 다른 결과로 기록됩니다.

검색 안에는 별도로 활성화하는 선택 호출이 하나 더 있습니다 — 언어별 질의 재작성은 켜져 있을 때만 실행되고, 실행되면 다른 호출과 마찬가지로 실제 호출로 기록됩니다.

요청이 끝나는 지점에 따라 결과는 이렇게 나뉩니다.

| 끝나는 지점 | 결과 | 성격 |
|---|---|---|
| 0. 경로 결정 | 고정 안내·서비스 범위 안내 | 인사·사용법 등의 고정 서비스 안내 또는 지원하지 않는 목적 — 문서 검토 판정이 아님 |
| 1. 질문 의도 확인 | 범위 안내 | 제공하지 않거나 모호한 기업·연도·범위 — `NOT_IN_DOCS`가 아님 |
| 근거 검토 | `NOT_IN_DOCS` | 유효한 범위를 검색했으나 근거 부족 |
| 근거 검토 | `SUPPORTED` | 인용이 검증을 통과한 답변 |
| 어느 지점 | 기술·운영 실패 | 카탈로그 조회·provider·시간 초과·예산 — 안내로 대체하지 않음 |

> **왜 일찍 멈추는가**: 제약 없는 LLM 답변이 더 유창하고 요청을 너그럽게 받아들이는 것처럼 보일 수 있지만, 사용 가능한 근거를 우회하고 제품의 범위를 실제보다 넓게 보이게 합니다. 명시적인 조기 안내는 더 제한적이고 사용자에게 질문을 다시 정리하게 만들지만, 근거와 실행 이력을 신뢰할 수 있게 유지합니다. 이 판단은 구조화 스키마와 인용 검증을 대체하는 것이 아니라 보완합니다.

화면에는 실제로 멈춘 단계와 이유가 표시되고, 실행되지 않은 뒷단계는 실패한 검사나 완료된 검증으로 기록되지 않습니다. 실제로 일어난 분류·모델 호출은 조기 종료에도 호출 수에 포함됩니다 — provider 재시도나 1회의 스키마 복구도 무상 복구가 아니라 측정된 호출입니다. 이 판단 규칙은 DEV와 PROD가 공유하고, 두 환경은 권한·모델·준비 제어만 다릅니다 — PROD가 별도의 자유 대화 제품은 아닙니다. 과거 실행 기록은 당시 결과를 그대로 보존합니다.

<!-- heading-alias: 1-6-평가와-실행-기록 -->
### 1-6. 평가와 실행 기록 {#evaluation}

검색 품질을 감으로 판단하지 않기 위해 골든 데이터셋과 평가 프레임워크를 만들었습니다. 정답 span을 원문 위치(`doc_id + sha256 + start/end`)로 고정하고, span 커버리지 0.5 이상을 적중으로 봅니다.

$$
\begin{aligned}
\mathrm{span\_coverage} &= \frac{|\mathrm{overlap}|}{|\mathrm{gold\ span}|}\\[0.8em]
\mathrm{recall@}k &= \frac{\text{hit gold spans}}{\text{gold spans}}\\[0.8em]
\mathrm{hit\_rate@}k &= \mathbf{1}\big[\text{top-}k\text{ contains a hit}\big]\\[0.8em]
\mathrm{RR} &= \frac{1}{\text{first hit rank}}\\[0.8em]
\mathrm{MRR} &= \mathrm{mean}(\mathrm{RR})
\end{aligned}
$$

## 2. AI 협업 개발 루프: 반복은 줄이고 판단은 유지 {#ai-collaboration}

기존에는 구독형 서비스에서 코드 분석·개념 습득·일상 활용 정도로 AI를 썼습니다. 이 프로젝트에서는 온라인 벤치마크와 사례, 직접 테스트를 거치며 활용 범위를 넓혔습니다. 코드와 설계를 이해하는 일은 여전히 중요하지만, **내가 이해하고 있는 부분을 명확히 예시로 주고 실행을 맡기면 결과가 비교할 수 없을 만큼 빨라진다**는 것을 체감했습니다.

작업 루틴은 이렇게 자리 잡았습니다.

- 상세한 구상을 먼저 던진다.
- 초안을 받아 대화로 좁힌다.
  - 설계: 계획을 작성하고 검토·수정한 뒤 실행
  - UI: 라이브 데모를 띄워 두고 지시사항을 입력해 즉시 수정
  - 그 밖의 목적에 맞게 조정

모든 것을 AI에 맡기는 것은 여전히 위험하다고 생각합니다. 대기 시간과 비용이 있고, 결과가 항상 만족스럽지도 않습니다. 다만 디버깅이 오히려 더 오래 걸려 비효율이 커지는 상황은 없었습니다.

<!-- heading-alias: 반복-작업에서-특히-도움이-된-것 -->
### 반복 작업에서 특히 도움이 된 것 {#repetitive-work}

- **질문·평가셋 준비**: 영문·한국어 질문을 데이터셋 성격에 맞게 생성하고, 파싱한 문서를 읽으며 어떤 질문이 적합한지 대화로 정리해 테스트셋을 준비했습니다.
- **테스트 코드**: 구현과 함께 테스트를 생성·수정하고, 모듈 미러 구조(`app/X/y.py` → `tests/X/test_y.py`)로 유지했습니다. 인제스천·검색·워크플로·평가·API 계약 테스트를 나눴고, 실제 DB가 필요한 스키마 검증은 `live_postgres` 마커로 분리해 격리된 PostgreSQL에서만 실행했습니다.
- **공개 API 한계 설계**: IP당 10회/분·50회/24시간, 호출당 \$0.005, UTC 일일 \$0.10 예약 상한. 임베딩·답변 호출 모두 실제 호출 직전에 상한을 예약하고, 영속 SQLite 원장으로 원자 처리합니다(단일 호스트 범위). SDK 자동 재시도는 비활성화해 상한을 우회하지 못하게 했습니다.
- **클라우드 비용 계산**: e2-medium 온디맨드 약 \$0.034/h(월 약 \$25) + 30GB 디스크 약 \$1 → 월 약 \$26. 임시 IP 무료(고정 예약 시 +\$3), Firebase·Cloudflare 무료 등급, OpenAI는 일일 \$0.10 상한. 약정(CUD)·spot으로 절감 가능.
- **실패 진단 설계**: workflow budget / provider failure / node error를 구분하는 오류 체계를 함께 설계했습니다. 어떤 자원이 왜 막혔는지 재현 가능하게 남기는 것이 기능 추가만큼 중요했습니다.

<!-- heading-alias: 고도화와-개선 -->
### 고도화와 개선 {#improvements}

- 구현을 상의하며 다른 사례를 빠르게 조사할 수 있었고, 정보 습득 속도가 확실히 빨라졌습니다.
- AI를 활용하면서 반복적인 구현과 테스트에 드는 시간을 줄일 수 있었고, 그렇게 확보한 시간을 사용 경험을 다듬는 데 많이 썼습니다. UI의 시각적 완성도나 디자인 감각은 아직 배우는 중이지만, 사용자가 무엇을 해야 하는지 이해하고 원하는 작업을 끝까지 수행할 수 있도록 만드는 데 집중했습니다. 직접 화면을 사용하면서 다음 단계가 명확한지, 설정과 실행 결과를 이해할 수 있는지, 문제가 생겼을 때 다시 진행할 방법을 찾을 수 있는지를 반복해서 확인하고 개선했습니다.
- 코드 조회와 에러 대응이 빨라졌습니다. "이 부분을 지우면서 남은 호환 코드를 정리해줘", "이 회사의 이전 평가 결과와 에러 원인을 비교해줘" 같은 요청을 즉시 처리할 수 있었습니다.

<!-- heading-alias: 한계와-대응 -->
### 한계와 대응 {#tradeoffs}

대기·비용·불만족은 분명히 있었습니다. 이를 줄이기 위해 **작업의 목표와 검증 방법을 정리하고, 작업 공간을 나누며, 다음 작업에 필요한 맥락을 남기는 흐름**을 직접 만들고 개선 중입니다. 화면을 보며 즉시 피드백하는 방식도 함께 사용했습니다. 반복해서 수정해도 요구사항과 검증 결과를 이어갈 수 있었지만, 토큰 사용량과 대기 시간은 여전히 관리해야 할 비용입니다.

이 프로젝트는 기능 구현뿐 아니라 **개발 프로세스 자체를 개선하는 실험**이기도 합니다. 도구를 쓰는 데 그치지 않고, 어떤 작업을 어떤 단위로 나누고 어떤 증거를 남길지 스스로 결정하며 진행하고 있습니다.

<!-- heading-alias: prod-dev-차이 -->
### PROD / DEV 차이 {#runtime-modes}

- **PROD**: 파싱·청킹·임베딩이 끝난 코퍼스를 DB에 적재한 상태로, 공개 조회·검색·답변·게시된 스냅샷만 제공합니다. 관리자 기능과 로컬 엔진은 비활성화됩니다.
- **DEV**: 수집·파싱·청킹·임베딩·평가까지 전체 파이프라인을 실행할 수 있고, 관리자 화면과 로컬 모델 연결을 사용할 수 있습니다.

<!-- heading-alias: 남은-일과-한계 -->
### 남은 일과 한계 {#remaining-work}

- 실제 클라우드 배포와 공개 운영은 아직 하지 않았습니다. 이 문서는 확정한 스펙과 절차를 기록한 것입니다.
- 답변 품질의 최종 확인(사용자 검수)과 하이퍼파라미터·대안 알고리즘의 폭넓은 실험은 시간상 남겨 두었습니다. 대신 평가 프레임워크와 재현 가능한 실행 기록을 남기는 쪽을 택했습니다.
- 라이브 사용자 트래픽, 장애 대응, 비용 실측은 배포 이후의 과제입니다.

<!-- heading-alias: 느낀점 -->
### 느낀점 {#reflections}

- 다른 프레임워크를 쓰지 않은 이유는 이 프로젝트를 통해 RAG를 직접 이해하고 싶었기 때문입니다. LangChain/LangGraph는 튜토리얼로 학습했지만, 코어 RAG와 워크플로는 직접 구현하는 쪽을 택했습니다. 프레임워크가 감추는 부분을 직접 만져보는 것이 목적이었습니다.
- RAG 파이프라인은 개념만 보면 단순합니다. 문서를 나누고, 벡터화하고, 질문으로 검색해 모델에 넘깁니다. 하지만 **성능을 개선하고 배포하는 일은 전혀 다른 문제**입니다. 파이프라인·알고리즘·하이퍼파라미터를 하나씩 조정하다 보면 왜 복잡해지는지 이해됩니다. 이 프로젝트를 하며 RAG의 검색-생성 루프를 직접 만들어 보면서, 도구 호출과 상태를 다루는 agentic 흐름으로 확장해 생각하게 됐습니다.
- 결국 **품질은 모델 교체보다 데이터(파싱·청킹·평가셋)에서 결정된다**는 것을 확인했습니다. AI가 줄여준 건 구현과 테스트를 치는 시간이고, 표를 어떻게 복원할지·한국어 질의를 어떻게 색인할지·골든셋에 무엇을 넣을지처럼 "무엇이 맞는가"를 정하는 일은 여전히 직접 판단해야 했습니다. 일정 대부분이 표 파싱, 한국어 검색, 골든셋, 언어 간 parity에 들어간 이유입니다.
- AI와 일하는 방식도 배웠습니다. 방향과 최종 승인은 제가 책임지고, 반복 구현과 검증은 AI와 함께하는 것이 지금의 기준입니다. 이 경험은 자연스럽게 다음 실험으로 이어졌습니다. 작업을 나누고 검토하는 일은 추론에 강한 모델에, 구현은 더 가벼운 모델에 맡기면 어떨까? 이 흐름을 반복하고 여러 작업을 동시에 진행하면서도, 문맥과 진행 상태를 유지하고 비용을 관리할 수 있을까? 요즘은 그 답을 직접 돌려 보며 확인하고 있습니다. 😎
