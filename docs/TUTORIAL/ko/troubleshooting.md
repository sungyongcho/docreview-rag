# 기록된 오류에서 원인 찾기

정확한 화면·작업·오류부터 확인합니다. 보이는 증상과 확인된 원인을 구분하고, 원인을 모르면 모르는 상태로 둡니다.

직접 관련된 상태부터 확인해 해당 문제만 고친 뒤 원래 동작을 다시 검증합니다. 요청 실패의 일반적인 해결책으로 전체 초기화를 사용하지 않습니다.

## 질문 범위 정보를 불러올 수 없음 {#manifest-scope}

경로 결정 전에 발생한 `query_scope_unavailable` 오류는 **0. 경로 결정**에 실패로 표시되고 1–5단계는 실행되지 않은 상태로 남습니다. 경로 결정 뒤 범위를 해석하다 실패하면 1단계에 표시됩니다. DEV의 기존 답변 실패 카드에는 파일 없음·JSON 형식 오류·manifest 규칙 위반·별칭 충돌·권한 오류 중 실제 원인, manifest 경로, **문서 목록 열기** 또는 **작업 열기** 동작 하나가 표시됩니다. 최근 원문 수집 작업은 진단 참고 정보이며 오류를 일으켰다는 증거는 아닙니다. 대기·실행 중인 작업이 있으면 완료 후 다시 시도하세요.

표시된 파일을 확인하고 `rag-schema check` / `rag-corpus status`로 점검하세요. 입력을 고친 뒤 질문을 다시 제출하면 됩니다. 실패한 지연 로드는 캐시되지 않으므로 API를 재시작할 필요가 없습니다. 수집은 manifest를 원자적으로 게시하므로 독자는 완전히 기록된 파일을 읽습니다. **실행 상세 → 트레이스**에는 민감 정보를 제거한 원래 예외 문구가 남습니다. PROD에서는 현지화된 제목과 일반적인 재시도 안내만 표시합니다.

## 페이지·API·DB에 연결되지 않을 때 {#connection}

> [!DEV]
> 로컬 서비스 복구나 호환되지 않는 스키마 진단은 개발 환경 운영자의 작업입니다. 공개 사용자는 표시된 연결 오류를 확인할 수 있습니다.

**시스템 → 시스템 상태**를 보고, 페이지가 열리지 않으면 터미널 로그를 확인합니다.

```bash
rag-dev ps
rag-dev logs --tail=80 web
rag-dev logs --tail=80 app
```

| 증상 | 근거와 원인 | 조치 | 확인 |
|---|---|---|---|
| 페이지가 열리지 않음 | APP_PORT·해당 포트의 프로세스/컨테이너·웹 로그를 봅니다. 페이지 실패만으로 DB 문제라고 단정하지 않습니다. | 설정된 주소를 열고 실패한 웹 서비스를 복구합니다. | 앱과 문서 페이지가 열립니다. |
| API 연결 실패 | 상태 응답과 앱 로그를 읽습니다. | 보고된 앱 연결·시작 오류를 고칩니다. | 시스템 새로고침에서 API 정상 상태를 확인합니다. |
| DB 연결 안 됨 | DB 상태와 연결 오류를 읽습니다. | 기존 데이터를 보존하며 의도한 DB 연결을 복구합니다. | 연결 성공 후 스키마를 별도로 확인합니다. |
| `schema_drift` | 저장된 스키마와 현재 모델이 다릅니다. | 기존 DB를 그대로 보존하고 비어 있는 별도 DB나 호환 DB를 선택합니다. | 호환 상태와 원래 작업의 동작을 확인합니다. |
| 작업 버튼 사용 불가 | DEV/PROD와 서버가 허용한 기능을 봅니다. | 운영 작업이 허용된 로컬 개발 환경을 사용합니다. | 필요한 개별 기능이 사용 가능한지 확인합니다. |

스키마 불일치가 확인되면 진단에 나온 테이블·열 정보를 기록합니다. 시작 과정은 호환되지 않는
DB를 변경하기 전에 중단됩니다. 기존 DB를 보존하고 이 체크아웃에 맞는 빈 별도 DB나 호환 DB를
선택한 다음 원래 작업을 다시 확인합니다.

안전한 시작과 스키마 확인은 [환경 준비](environment.md), [CLI 참고](cli.md)에 있습니다.

## 필터나 검색 근거가 질문과 맞지 않을 때 {#retrieval}

대화의 범위·필터와 **데이터 준비 → 문서**, **품질 검증 → 1. 검색 테스트**를 확인합니다.

| 증상 | 근거와 원인 | 조치 | 확인 |
|---|---|---|---|
| 필터 입력 중 전송 불가 | 강조된 임시 입력·범위별 선택지·사용 불가 칩을 봅니다. | 입력을 고치거나 맞지 않는 선택을 직접 제거합니다. | 잘못된 입력이 없고 요청 미리보기에 의도한 필터가 표시됩니다. |
| 필터 선택지 로드 실패 | 패널의 요청 오류와 재시도 버튼을 봅니다. | 목록 요청을 복구하고 재시도합니다. 진단 중 선택값은 보존합니다. | 현재 범위의 회사·연도·보고서 종류·언어가 로드됩니다. |
| 예상 문서가 없음 | 회사·연도 필터, 원문 식별자, 공개 소속을 봅니다. | 검색을 고치고 필요한 경우에만 데이터를 준비합니다. 공개 화면이라면 적재 실패로 단정하지 말고 게시 상태를 봅니다. | 적절한 문서 목록에서 확인됩니다. |
| 임베딩 누락·구버전 | 제공자·모델·차원·저장 식별자·미처리 개수를 봅니다. | 설정을 고친 뒤 필요한 범위를 의도적으로 보충합니다. 비용이 발생할 수 있습니다. | 현재 식별자가 맞고 미처리 상태가 해소됩니다. |
| BM25 사용 불가 | 파이프라인 키워드 준비 상태와 작업 결과를 봅니다. | 없거나 무효화된 BM25 통계를 재구축합니다. | 작업 성공과 BM25 준비를 확인합니다. |
| `NOT_IN_DOCS` | 실제 라우팅·후보·원문 구절을 읽습니다. | 문서가 뒷받침하는 질문을 하거나 범위를 고칩니다. | 의도한 질문의 근거를 찾고, 근거 없는 주장을 만들지 않습니다. |

개발 DB가 채워져 있어도 공개 문서 목록은 비어 있을 수 있습니다. [스냅샷 공개 범위](snapshots.md#visibility)를 확인하세요. 전체 공시 수가 표시돼도 선택한 SEC/DART 범위의 크기를 뜻하지는 않습니다.

## 검토가 실패하거나 오래 걸릴 때 {#execution}

답변의 **실행 트레이스·실행 성능**을 열고, Run ID·원래 노드 이름·정확한 실패 필드를 보존합니다.

| 실패 | 근거 | 검토할 수정 | 확인 |
|---|---|---|---|
| `budget_exceeded` | `resource`, `limit`, `observed`, `blocked_node` | 필요에 맞게 대화 설정 → 실행 한도의 해당 누적 한도만 조정합니다. | 의도한 새 실행이 정한 한도 내에서 동작합니다. |
| `provider_failure` | `status`, `attempts`, `details`, `node` | 보고된 인증·주소·제공자 한도·시간 초과·출력 형식 문제를 고칩니다. | 관련 없는 설정 변경 없이 해당 제공자 호출이 성공합니다. |
| `provider_failure`에 `budget.projected_input_tokens`가 있는 경우 | 프롬프트가 남은 입력 허용량을 넘길 것으로 추정돼 전송하지 않았습니다. | 대화 설정 → 근거의 최대 컨텍스트를 낮추거나 `budget_source`가 가리키는 입력 한도를 올립니다. | 다시 실행하면 호출이 전송되고 실제 사용량이 기록됩니다. |
| `node_error` | `error_type`, `message`, `node` | 지정된 비모델 단계에서 구체적인 원인을 확인합니다. | 새 시도에서 그 단계가 완료됩니다. |
| 측정 정보 없음 | 미수집 필드나 오래된 저장 기록입니다. | 누락 상태를 유지하고 적합한 실제 실행의 측정값이 있을 때 사용합니다. | 시간 관련 설명이 수집된 근거와 맞습니다. |

기본 시간 한도는 **실행 전체의 120초**이며 모델 호출 한 번의 시간이나 토큰 예산이 아닙니다. 근거 크기는 별도 설정입니다. 연결 실패는 토큰 한도를 높여 고치지 않습니다. 경과 시간만으로 CPU/GPU 배치나 특정 모델 병목을 단정하지 않습니다.

로컬 서버라면 **설정 → 로컬 LLM**과 선택한 답변 가능 모델을 확인합니다. 새 연결 검색·저장에 실패하면 동작하던 기존 연결을 보존합니다. [실행 안내](runtime.md#local-models)와 CLI 진단으로 백엔드가 서버에 접근하는지 확인하세요. 답변 엔진이 로컬이어도 재검토 과정의 임베딩 등에는 비용이 발생할 수 있습니다.

## 평가·초안·스냅샷이 막혔을 때 {#evaluation}

**품질 검증 → 2. 평가 데이터셋 준비 / 3. 평가 실행 / 4. 결과 비교·보관**과 **데이터 준비 → 작업**을 확인합니다.

| 증상 | 근거와 원인 | 조치 | 확인 |
|---|---|---|---|
| 원문 사용 불가 | Suite의 원문 오류와 필요한 manifest 항목을 봅니다. | 지정된 원문과 인덱스를 준비한 뒤 해당 suite를 평가합니다. | 원문 준비가 확인되고 의도한 평가를 접수할 수 있습니다. |
| 초안 저장·검증 실패 | 지정된 질문·참고 답변·해시·문자 범위 필드를 봅니다. | 편집용 초안의 해당 필드를 고치고 저장 후 검증합니다. | 의도한 리비전의 검증이 성공합니다. |
| 이동 시 변경 취소 확인 | 저장하지 않은 질문이 있습니다. | 보존하려면 취소하고, 버리려는 경우에만 명시적으로 선택합니다. | 초안과 돌아갈 위치가 유지됩니다. |
| 작업 중단 | 재시작이 실행을 끊었습니다. | 완료 상태를 읽은 뒤 필요하면 지원되는 새 작업 재시도를 사용합니다. | 새 작업의 상태와 기대한 결과를 확인합니다. |
| 비교 결과 없음 | 서로 다른 결과가 두 개보다 적거나 적합한 쌍이 선택되지 않았습니다. | 적합한 기록을 고르고 불가능한 비교는 빈 상태로 둡니다. | 선택한 쌍의 메타데이터와 실제 지표가 나옵니다. |
| 스냅샷 저장 거부 | 조합별·과거 결과의 현재 인덱스 식별자가 없거나, 원문 fingerprint·정답 식별자가 달라졌습니다. | 일치하는 빠른 평가 결과를 고릅니다. 필요하다면 의도한 현재 corpus를 평가합니다. | 적합한 결과의 스냅샷이 저장 목록에 나타납니다. |

[데이터셋 편집](evaluation.md#golden)과 [비교 조건](snapshots.md#comparison)을 참고하세요. 화면에 나온 설명용 예시를 실제 평가가 실행됐다는 근거로 삼지 않습니다.

## 작업 이력 관리 {#job-history}

작업 화면에서 **이력 관리**를 엽니다. **이력 동기화**는 서버 상태를 다시 읽으며 작업을 재실행하지 않습니다. **완료된 작업 보관**은 종료된 기록을 일반 목록에서 숨기고, **보관된 작업 복원**은 다시 표시합니다. 대기·실행 중 작업과 원문 파일·임베딩·평가 결과는 보존합니다.

**작업 이력 삭제**는 표시 중이거나 보관된 종료 작업의 기록만 영구 삭제합니다. 표시된 개수를 확인하고 `DELETE JOB HISTORY`를 입력합니다. 서버는 먼저 전체 기록의 비공개 백업을 만들어야 하며, 백업에 실패하면 기록을 그대로 유지합니다. 성공 후 **작업 이력 백업 다운로드**로 백업을 받을 수 있습니다. 대상 개수가 달라지면 동기화한 뒤 다시 확인하세요. 보관 복원은 삭제한 백업을 다시 가져오지 않으며 어떤 동작도 작업을 자동으로 재실행하지 않습니다.

## 전체 초기화: 삭제 전에 사용 가능 여부 확인 {#reset}

> [!DEV]
> 실행 데이터 초기화·가능 여부 검사·복구 조작은 개발 모드와 로컬 운영자 권한이 필요합니다. 공개 화면에서는 실행 데이터를 삭제할 수 없습니다.

**데이터 준비 → 파이프라인** 왼쪽 위의 빨간 **실행 데이터 초기화** 버튼을 누르면 모달 창이 열립니다. 창을 열거나 닫는 것만으로 데이터가 초기화되지는 않습니다. **초기화 가능 여부 확인**은 읽기 전용 검사이며 확인 중·가능/차단·**마지막 점검** 시간을 표시합니다. 삭제 미리보기와 마찬가지로 관련 런타임 파일 권한·실행 중인 DB 작업·활성 앱 요청을 확인합니다.

차단되면 **초기화 진단**의 코드·파일과 부모 디렉터리 정보·수동 해결 방법을 읽습니다. 권한 진단에는 실제 운영자 UID/GID와 파일·폴더 소유자 및 모드가 나옵니다. 앱이 쓸 수 있는 파일도 다른 사용자로 실행되는 호스트 운영자에게는 접근 불가일 수 있습니다. 검사는 소유권·권한·ACL을 바꾸지 않습니다.

소유자의 승인 아래 보고된 원인만 해결하고 다시 확인합니다. 실행 중인 코드와 저장소의 수정본이 다르면 소스 재로딩이 필요할 수 있습니다. 운영자 재시작은 별도 작업입니다. 먼저 활성 작업·초기화가 없는지 확인한 뒤 개발 서비스와 DB를 보존하며 해당 운영자만 다시 올립니다. 초기화가 막혀도 관련 없는 앱 작업은 계속할 수 있습니다.

정말 삭제하려는 경우 **실행 데이터 전체 삭제**를 누르면 **모든 런타임 데이터를 삭제하시겠습니까?** 질문과 정확한 대상 미리보기가 열립니다. 되돌릴 수 없다는 경고를 읽으세요. 자동 백업과 실행 취소는 없습니다. **취소**는 삭제하지 않고 창을 닫습니다. 현재는 `WIPE <project-name>` 형태로 표시되는 확인 문구를 정확히 입력한 뒤 **이 실행 환경의 데이터를 영구 삭제**를 사용합니다. 프로젝트 이름이 포함된 미리보기에서 `WIPE`만 입력하면 안 됩니다.

초기화 대상은 런타임 DB 기록·다운로드한 공시·생성된 평가 산출물·저장 연결입니다. 코드·인증 정보·`.env`·튜토리얼 이미지·manifest/golden/profile 원본은 미리보기에 나온 보존 목록을 따릅니다. 서버 성공 후에만 **브라우저 데이터를 지우고 다시 시작**으로 이 앱의 브라우저 상태를 지웁니다.

실패·중단 시에는 이미 삭제된 데이터가 있을 수 있으므로 완료 단계와 복구 안내를 먼저 읽습니다. 기록 상태를 확인한 다음 제공된 복구 동작으로만 초기화 잠금을 해제합니다. 데이터를 유지하는 일반 종료와 재시작은 [다시 시작하기](runtime.md#resume)를 사용합니다.

## 일시적인 상태 확인 실패

첫 실패 검사를 시작한 시각부터 20초 유예를 두고 다음 재확인 시 장애를 확정합니다. 재시도 간격은 3초이며 health와 readiness에는 각각 5초 제한을 적용합니다. 유예 중에는 마지막 확인 상태를 유지하고 화면을 막지 않는 대기 알림을 표시합니다. 실행·대기 중인 작업이 있으면 알림에 함께 안내하며 정상 확인 후 제거합니다.

`/health`가 성공하고 `/ready`만 실패하면 API가 살아 있으므로 중단으로 표시하지 않습니다. liveness는 3초 간격, readiness는 최소 10초 간격으로 확인합니다. 브라우저 offline 이벤트는 루프백 API 중단의 증거로 삼지 않고 즉시 재검사합니다. 실제 실패에는 같은 유예 시간을 적용합니다. 정기 검사는 이미 정상인 `kind`를 checking으로 바꾸거나 전송 버튼을 비활성화하지 않으며 변경 작업을 자동 재시도하지 않습니다.

로컬 명령이 실행되는 동안 **시스템 → 로컬 작업**은 1초 간격(숨긴 탭에서는 5초)으로 상태를 확인합니다. 실패하면 간격을 2·4·8·10초로 늘리고, 세 번 연속 실패하면 실패마다 오류 알림을 띄우는 대신 대기 알림 하나만 표시하며 다음 성공 시 제거합니다. 수동 **새로 고침**의 오류는 그대로 표시합니다. [로컬 작업](runtime.md#operations)을 참고하세요.

`/ready`는 자주 불러도 부담이 적습니다. 서버는 스키마·개수 판독을 최대 2초, 코퍼스나 평가 작업이 실행 순서를 잡고 있거나 기다리는 동안에는 최대 10초 동안 재사용하고, 작업이 끝나면 곧바로 다시 잽니다. 애플리케이션 밖에서 바꾼 스키마는 그만큼 늦게 보일 수 있으며, 쓰기 경로는 항상 스키마를 새로 확인합니다. `python -m scripts.diagnostics.readiness --base-url http://127.0.0.1:8001 --ingest tutorial`은 격리 스택에서 적재 작업 전·중·후의 `/health`·`/ready` 지연을 기록합니다.

**빌드 → 작업**과 상단 작업 카운터 뒤의 작업 보드는 작업이 실행 중이면 1초, 유휴 상태면 5초, 숨긴 탭에서는 15초 간격으로 확인합니다. 확인에 실패하면 마지막 보드를 그대로 두고 작업 센터에 "최신이 아닐 수 있음" 상태 줄을 표시하며, 토스트 없이 2·4·8·10초 간격으로 다시 시도합니다. 수동 **새로 고침**의 오류는 그대로 표시합니다. 코퍼스 상태·문서 필터·평가 실행·스냅샷 같은 관리자 읽기 요청은 15초가 지나면 "요청 시간 초과"로 끝나고, 쓰기 요청에는 시간 제한이나 자동 재시도가 없습니다. **빌드 → 파이프라인**은 네 가지 읽기를 각각 독립적으로 갱신해 실패한 항목은 마지막 상태를 유지하고 인라인 안내를 표시하며, 직접 새로 고침을 눌렀을 때만 토스트를 띄웁니다.

## 연결 상태와 알림 {#connection-feedback}

API 연결 확인은 상태이며 별도의 환경이 아닙니다. 서버에서 확인한 환경에만 DEV/PROD 배지를 표시하고, 첫 연결 전에는 제3의 모드를 만들지 않습니다. 연결 확인이나 지연된 재시도 중에는 Build 준비 상태를 중립적으로 표시하고 실행을 비활성화합니다. 이전의 초록색 준비 완료 표시는 현재 연결의 증거가 아닙니다. 복구 후 실제 API·인덱스 상태를 확인해야 준비 완료로 돌아오며, 공개 데모 데이터 표시는 구분해서 유지합니다.

연결 지연은 입력창 위를 가리는 고정 토스트 대신 **연결 다시 확인** 버튼이 있는 상태 행으로 표시합니다. 저장·작업 결과는 화면 헤더 아래의 알림 공간이나 현재 설정 대화상자·실행 상세 패널 안에 표시해 입력과 버튼을 덮지 않습니다. 좁은 화면이나 키보드가 올라온 화면에서는 제한된 높이 안에서 스크롤하고, 긴 메시지는 직접 펼쳐 읽을 수 있습니다.

같은 내용의 반복 알림은 하나만 유지하며 타이머를 재시작하지 않습니다. 마우스를 올리거나 키보드 초점을 두거나 메시지를 펼친 동안에는 자동 닫기를 멈춥니다. 닫기 버튼으로 제거할 수 있고 지속 경고는 해결되거나 직접 닫을 때까지 유지됩니다. 백엔드 재시도·작업 전달 규칙은 바뀌지 않습니다.
