# M9 조사 결과 — 고정 워크플로가 할 수 없는 것

## F1 — 워크플로의 경로는 질문이 아니라 코드가 고른다

M4는 모든 요청에 대해 retrieve → grade → check → report를 실행한다. 단일 리뷰 질문에는 정확히 맞는 구조지만, 다른 경로가 필요한 작업에는 정확히 틀린 구조다. 두 회계연도를 비교하려면 필터가 다른 검색이 두 번 필요하고, 모호한 질문은 첫 근거를 읽은 뒤의 후속 검색이 필요하다. 고정 그래프는 실행 중에 경로를 다시 짤 수 없다.

## F2 — 멀티홉 질문은 단일 질의에서 recall을 잃는다

M3 골든셋은 설계 단계부터 `multi_hop` 카테고리를 갖고 있다. 두 사실을 잇는 질문("X가 2023년과 2024년 사이 어떻게 변했나")은 섞인 질의 임베딩 하나와 섞인 lexical 질의 하나로 검색하므로, 밑에 깔린 각 사실이 서로 top-k 자리를 놓고 경쟁한다. 스위트 전체 점수는 이것을 숨긴다. 갭은 지표를 카테고리별로 잘라야만 드러나며, `app/agent/eval.py`가 존재하는 이유가 바로 그것이다.

## F3 — 모델에게 경로를 넘기려면 계약은 더 단단해져야 한다

모델이 도구를 고르게 하면 실행이 어긋날 수 있는 경우의 수가 늘어난다. 존재하지 않는 도구, 형식이 깨진 인자, 조작된 관찰, 지어낸 인용, 무한한 지출. 이 실패 계급 하나하나에 이미 M4 시절의 답이 있었다 — 타입이 있는 실패, 예산 가드, 인용 교집합 검사 — 그리고 M9는 새 장치를 발명하는 대신 그 각각을 루프 경계에서 재사용한다.

## F4 — 하나의 도구 스키마가 세 소비자를 먹여야 한다

모델은 프롬프트 매뉴얼을 읽고, API는 function spec을 받고, MCP 클라이언트는 input schema를 가져간다. 셋을 따로 쓰면 반드시 어긋나고, 여기서 어긋남은 모델이 존재하지 않는 도구를 호출하거나 MCP 클라이언트가 도구가 거부할 인자를 보내는 것을 뜻한다. 레지스트리는 셋 모두를 같은 `Tool` 선언에서 생성하므로, 어긋남은 구조적으로 불가능하다.
